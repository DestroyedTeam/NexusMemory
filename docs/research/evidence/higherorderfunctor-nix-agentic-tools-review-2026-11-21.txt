WHAT IT ACTUALLY DOES — HIGH-VALUE FOR RESOURCE/CONFIG PLANE
- Root README says it manages stacked workflow skills, MCP servers, and declarative config for AI coding CLIs. It can install/copy skill packages without Nix; Nix adds overlays plus Home Manager/dev-environment modules.
- Shared `ai.*` schema models context, rules, skills, agents, hooks, MCP servers, settings, environment variables, shell, proxy, reasoning effort, Git config, package installation and inference endpoints. Generated native configuration is runtime- and backend-specific, capability-gated, and several unsupported requests warn rather than silently being treated as portable. Home Manager and devenv differ in scope/ownership (user-global vs project-local); generated files are often read-only copies with project-trust and path constraints.
- Runtime distinctions matter: Claude Code CLI, Codex CLI, Kiro CLI and some Kimchi surfaces receive settings/resources; github.com Copilot is configured through committed `.github/` files in devenv, not through Home Manager, and this `ai.copilot` surface is not Copilot CLI settings. Copilot CLI is packaged separately. Do not equate a product family name with interchangeable runtimes.
- There are 14 packaged MCP servers and typed `ai.mcpServers` configuration; `redact.file`/`redact.command`/`redact.concat` prevent raw credentials from being embedded directly in generated Nix-store values. The feature matrix also models a CliproxyAPI-style inference plane: a named instance, client key, upstream credentials and ordered routes can feed Claude Code `/model` rows and Codex model discovery. This is relevant to local API-key gateway configuration, not a Claude Desktop Chat/Cowork/Code session connector.
- The repo has no ChatGPT/Codex Project, Section Group, conversation/session/branch import/export, attachment/token ledger, scheduled-task converter, or unified history database. `chatgpt-codex` is a Codex CLI package, not a ChatGPT Projects importer. Its `docs/agentic-harness-handoff.md` (dated 2026-05-08) is a handoff/spec for a prospective sequential `claude -p` runner with `session_id`/`--resume` and shell accept scripts; a targeted source search found this contract only in the handoff document, not an implemented product/session migrator.

KIRO SESSION RESEARCH — HIGH VALUE BUT VERSION-BOUND
- The repo contains `docs/plans/kiro-v3-research-raw/phase2/f19-session-store.md` and `acp-live-probe.md`: explicit provenance says verified 2026-07-30 against KAS/Kiro CLI 2.15.1 (one companion argv document measured 2.15.2). The F19 writeup analyzes a corpus of 212 sessions from one machine and 56,195 root + 29,829 sub rows; treat these aggregate counts as historical research evidence, not universal coverage.
- The old F19 schema maps a bucket/session tree, `session.json`, `messages.jsonl`, flat `sub-executions/<id>.jsonl`, content-addressed file snapshots, workflow state, cursors and large-tool-output sidecars. Session metadata includes parent session/execution links, created reason, workspace paths, repo bindings, execution target, model/effort fields and context files. The 23-message union includes user images/documents/context URIs, assistant/tool events, sub-agent lifecycle, steering inclusion, turn lifecycle, tombstones, hook events, pending interactions, usage summaries and session metadata. Sub-execution files are flat and joined by IDs, not nested by hierarchy depth.
- This is valuable structure evidence for a Kiro source adapter, but its own limitations are substantial: usage is metered in credits rather than raw token counts; the effective model is only stamped on some reasoning messages and per-dispatch effort is unrecoverable; `agentInitiated` turns may have no user row. Its 2.15.1 `_kiro/session/export` probe wrote a zip of session.json/messages.jsonl/sub-executions outside the scratch HOME, and the F19 bundle inspection says it omitted snapshots, cursors and tool-output sidecars. The live probe used five scripted stdio sessions, denied access-token requests, never sent a prompt, and made no model/credit call.
- Freshness warning: this repo now packages Kiro CLI 3.5.0, while the deep raw schema/API evidence is tied to 2.15.1/2.15.2. Current first-party Kiro docs say V3 changed the session format vs 2.x and is not backward-compatible; official current ACP guidance says storage is server-owned, do not write V3 files directly, use `session/list`/`session/load` and advertised export/history, and resend client-owned cwd/additionalDirectories/MCP inputs on load. The old F19 paths/fields must be revalidated against the exact current 3.5.0 build before implementation.
- Current official Kiro CLI docs add a more reliable product contract: local CLI V3 sessions can be saved as ZIP and loaded; `save-via-script` receives session JSON on stdin and `load-via-script` supplies JSON on stdout. Cloud sessions use an account-side store and resume by ID across machines, but `/chat save`/`/chat load` are unavailable for cloud sessions. Workflow step sessions are not guaranteed to be independently searchable/exportable/resumable through the normal session dashboard. This supports separate `local-V3`, `cloud`, and historical `v2` adapters; it does not create cross-Harness conversion automatically.

FIT / RECOMMENDATION
- Retain as a high-value reference for deterministic harness capability matrices, typed config/resource placements, explicit backend/scope semantics, warnings for unsupported features, safe secret references, CPA gateway configuration, and Kiro’s historical session schema.
- Do not use it as the Nexus Memory transfer engine, do not assume its Kiro 2.15.1 session research is current for 3.5.0, and do not claim it handles ChatGPT/Codex Projects/Sections or Claude Desktop Chat/Cowork/Code history. Its current user-facing product is declarative CLI environment/config management; its Kiro session docs are research artifacts, not a reusable converter.
- Nexus Memory design takeaway: define `RuntimeCapability` and per-field preservation/loss reports; separately model `ResourcePlacement`, `ConversationProject`, `ConversationSession`, message/event edges, file snapshots, usage, and scheduler records; require versioned source adapters and file/native-API export imports instead of guessing from a shared skill/MCP format. Kiro supports a possible adapter contract through save/load scripts for local CLI V3, but cloud and local are different sources and historical v2 is separate.
