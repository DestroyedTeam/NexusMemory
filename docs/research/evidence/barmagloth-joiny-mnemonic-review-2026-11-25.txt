# Candidate #270 — Barmagloth/Joiny-Mnemonic (2026-11-25)

## Decision
**Strong architecture prior art for a local, agent-neutral memory substrate; not a historical-session or project migrator.** Keep it in the “memory / live-hook interoperability” lane, not as a completed Nexus Memory adapter. Do not claim it transfers ChatGPT Projects, Section Groups, Destruction Era session graphs, or creates target-native Claude Desktop/Claude Code sessions.

## What the implementation actually provides
- A local SQLite-backed, append-only event and artifact store with canonical-content hashes, previous/chain hashes, update/delete guards, `synchronous=FULL`, source adapter/channel provenance, and secret/private-region redaction. Events carry an internal branch ID, internal session ID, event kind/role/content, payload, file references and timestamps. Arbitrary native event payload is useful provenance, but is recorded only when an adapter/hook sends the event; it is not a parser for a historical archive.
- Its real connector list is exactly `claude-code`, `codex`, `opencode`, and `openhands`. These adapters normalize **individual future hook/native events**. `ClaudeCodeAdapter` observes hooks such as `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, and compaction; the Codex/OpenCode/OpenHands adapters have their own narrower event sets. `ingest_native()` accepts one event object; hook delivery resolves an external session ID to a newly generated Joiny session ID. The CLI help includes `ingest`, `hook`, `session-start`, `branch-create`, `resume`, and `install-hooks`, but no historical archive import/export or migration command. [Pinned adapters](https://github.com/Barmagloth/Joiny-Mnemonic/blob/0d3ad140563b5ea60e2b7ae14b78e0e1384d7f0b/src/joiny_mnemonic/adapters.py) · [event storage](https://github.com/Barmagloth/Joiny-Mnemonic/blob/0d3ad140563b5ea60e2b7ae14b78e0e1384d7f0b/src/joiny_mnemonic/event_storage.py) · [CLI](https://github.com/Barmagloth/Joiny-Mnemonic/blob/0d3ad140563b5ea60e2b7ae14b78e0e1384d7f0b/src/joiny_mnemonic/cli.py).
- It does have **Joiny-native** branches with parent/fork cursors and task hierarchy (`parent_task_key`), plus snapshots and replay-tail resume packets. The README caps the protected resume packet at 1,500 estimated tokens. This is useful internal context organization, not a source importer for ChatGPT Project/Section membership, parent/child conversation links, alternate assistant branches, coordinator/worker sessions, or target-native session state.
- An `Artifact` can store bytes with a content hash and MIME type. That capability is not evidence of an adapter extracting source attachments or restoring them in a destination. Likewise, the bundled MCP server exposes Joiny memory tools; optional plugins add semantic/knowledge graph/local extraction. These are not tools for discovering and moving another Harness's Skills, MCP servers, plugins, memory stores, scheduled tasks, credentials, or gateway configuration.

## Fit against the user's target matrix
| Target | Result at this pin |
|---|---|
| ChatGPT/Codex Projects + Section Groups | No ChatGPT adapter, export parser, project/section membership reader, or target writer. “Codex” means its live project-local hook integration, not ChatGPT account/project import. |
| Destruction Era and old session graphs | Can build its own event/branch/task graph and bind live external session IDs; no source archive parser for `conversations.json`, `mapping`, parent/child/fork/task graph, or historical session reconstruction. |
| Claude Desktop 3P Chat / Cowork / Code | No Desktop-local database, Chat/Cowork/Code, or gateway-mode adapter. Its `claude-code` adapter is a CLI hook integration only; it is not evidence that Desktop Code/Cowork/Chat stores can be read or recreated. |
| Local/self-hosted Claude Code via API key/gateway | Potentially useful to capture **future** local Claude Code hook events regardless of configured inference endpoint; no historical Claude Code transcript importer or native session writer/restore. No gateway-specific API is used by Joiny. |
| Skills, MCP/plugins, memory, attachments, schedules | Joiny supplies its own memory MCP and optional plugins; it does not migrate other tools' resource installations or scheduled jobs. Artifact storage is generic, not source attachment mapping. |

## Behavior and test evidence
- A temporary-home `joiny-mnemonic capabilities` probe exited 0, reported the four adapters above, all `hooks_configured=false` in the isolated project, `append_only=true`, `task_boundaries=task-branch-snapshot-resume`, and optional semantic/knowledge-graph features disabled by default. No provider call or external agent binary was launched.
- A separate initial capabilities invocation used the default `HOME`; the code checked only for Joiny-owned hook markers in global Claude Code/Codex/OpenCode config paths and reported no configured Joiny hooks. It did not read transcripts or API keys. Its test database and generated `.joiny-mnemonic`, `.pytest_cache`, editable-install metadata, `__pycache__`, and `tests/runtime` fixtures were removed afterward; the clone returned to clean Git status.
- Initial test-wrapper attempts: `rtk pytest tests/` exit 1 because the wrapper could not spawn a system pytest; direct `python -m pytest tests/` exit 1 because pytest was not installed. A disposable Python 3.12.4 venv with pytest 9.2.0 and editable `joiny-mnemonic` was used; that matches the repository CI's main install step. Its exact test step failed collection, exit 2, because `tests/test_stage6_conllu_graph_diagnostic.py` imports `joiny_mnemonic_local_llm` while `.github/workflows/pytest.yml` installs only `-e . pytest`, not `plugins/local-llm`.
- With the local-LLM package 0.4.0 additionally installed `--no-deps` (still in the disposable venv), the full suite exited 1: **486 passed, 8 failed, 1 skipped, 1 xfailed, 314 subtests passed**. The failures were: one complexity gate (`retrieval.py` has 1,089 lines versus the 1,000-line new-module limit); six digest mismatches in published Stage-6 diagnostic artifacts; and `test_telemetry_failure_never_fails_search_or_prompt` (a `RuntimeError` from telemetry bubbles out of `MemoryService.search`). Exact run output and six actual/expected digests are preserved in the transaction verification ledger.
- Focused `tests/test_integrations.py tests/test_ingress_equivalence.py` exited 0; output `.....................x...... [100%]` (one expected xfail). These tests validate normalized event ingress, not a real host binary, account, migration, or restore.
- No user transcript, session archive, API key, or model/provider endpoint was used. The one default-HOME check above was limited to checking hook-registration markers and was not a session-data read.

## Reuse recommendation
Keep only the **architecture patterns**: immutable canonical event log; provenance fields that distinguish source identity from Joiny IDs; branch lineage/fork cursors; task-boundary branches; receipts/idempotency; artifact hashes; and a separate live-hook ingestion plane. Do not copy Joiny wholesale or count it as migration. For Nexus Memory, the crucial missing addition would be versioned **historical source readers + target writers** that map both record graph and resource/project/section scope, preserve original payloads/asset bytes, and emit explicit fidelity/loss reports. Before any production integration, fix the reproducible CI install gap and test failures and exercise each exact host/version in an isolated profile.
