## Product boundary from source and docs

AY Claude CLI is a marketplace/package installer for Claude Code extension resources: Skills, agents, commands, hooks, plugins, MCP-labelled packages, and settings presets. `getClaudePaths()` hardcodes user scope to `~/.claude` and project scope to `cwd/.claude`; content folders include `skills`, `agents`, `commands`, `hooks`, `plugins`, `mcps`, and `settings`. The source explicitly comments that `~/.claude` is “not Claude Desktop paths.” It authenticates to the AY service with an OAuth device flow and a bearer token before search/download; it does not import ChatGPT/Codex exports or call an Anthropic/API-key gateway for session continuation.

Workspace data in `src/core/workspaces.ts` is a local list of members, packages, settings and a current workspace. It is not a conversation Project, Section group, Session, message, branch/fork, task run, attachment, token/cost record, or transcript. Search for `session|conversation|transcript|chatgpt|claude desktop|api key|gateway` found only generic mentions that Skills are available in Claude Code sessions, CLI auth “web sessions,” and a comment excluding Claude Desktop paths. No ChatGPT Project/Section or Claude Desktop Chat/Cowork/Code adapter/import/export was found. All three Desktop modes remain independently in user-confirmed scope.

The implementation writes into fixed `~/.claude` paths and does not consult `CLAUDE_CONFIG_DIR`. Current first-party Claude Code settings documentation says `CLAUDE_CONFIG_DIR` relocates settings, session history, and plugins; this makes the CLI mis-target custom-config users. The app's “MCP” flow reads a package-local `mcp.json` only to extract a server name and add it to `settings.enabledMcpjsonServers`; source does not establish transfer of server credentials, `.mcp.json`/`~/.claude.json` ownership, or an external-session dependency graph.

## Security and correctness findings (synthetic isolated probes only)

- README/security docs describe a five-stage security pipeline and claim path-traversal prevention/“production-ready” security. The source verifier performs an optional SHA-256 check (only if an expected hash is supplied), structural checks, and regex-based text scanning. `extractZip()` writes each JSZip entry to `path.join(destDir, entry)` without a containment check; `installPackage()` joins API-provided `selectedPackage.slug` into the content-type root without validating containment.
- A temporary POC invoked the actual `installPackage()` source with a safe synthetic Skill ZIP, sandbox HOME, and slug `../../../escaped-install`. It returned `/tmp/nm-ay-claude-poc/sandbox/escaped-install` and wrote `SKILL.md` there; the expected `/tmp/nm-ay-claude-poc/sandbox/home/.claude/skills/escaped-install/SKILL.md` did not exist. This proves an untrusted API slug can escape the intended content-type root if the backend allows such a slug; no live AY API or user directory was used.
- Forward-slash ZIP Slip input `../../escape-forward.txt` was sanitized by the declared JSZip 3.10.1 loader and the actual `extractZip()` wrote it only inside the chosen destination; the sibling escape path remained missing. This positive control is important: do not overstate this standard path as vulnerable on the tested version.
- However, JSZip 3.10.1 preserves ZIP entry `..\..\settings.json` as that key/`unsafeOriginalName`. A Node `path.win32.join` projection from `C:\Users\sandbox-user\.claude\skills\sample-skill` resolves it to `C:\Users\sandbox-user\.claude\settings.json`, outside the install root. `extractZip()` uses native `path.join` and has no path containment guard. This is a Windows path-traversal risk based on the exact package source plus a Windows-path projection; the ZIP write was not executed on a Windows host. The project advertises Windows support, so require a real Windows regression test and path validation before any adoption.
- A benign hook fixture `hook.sh` passed through actual `PackageVerifier.verifyPackage()` and was rejected with `{"valid":false,"errors":["Suspicious file detected: hook.sh"]}`. The repository's own `hook-basic` template creates `hook.sh`; this makes a documented built-in hook path incompatible with the verifier.
- Repository tree has no tracked `tests/` files or `.github/workflows` files. `rtk npm test` exited 127 with literal `sh: vitest: command not found`; dependencies were not installed in the source checkout. `gh run list --limit 5` produced an empty list. Do not claim automated test coverage or CI success.
- The package-name and ZIP probes wrote only beneath `/tmp/nm-ay-claude-poc`; the temporary `node_modules` symlink was removed, and the source checkout returned clean. No user home, Claude settings, API account, or live marketplace was touched.

## Disposition

**Exclude as Nexus Memory's session/project migration engine and do not use against user Claude directories or untrusted marketplace data.** At most retain it as a negative security/usability reference for a Claude Code resource-package UX: its package model is resource-plane-only, its auth/server dependency is proprietary to AY, its config path misses `CLAUDE_CONFIG_DIR`, the slug boundary is unsafe, Windows ZIP entry containment is unverified and likely escapable, and its built-in `.sh` hook template is rejected. It provides no evidence of portable ChatGPT Project/Section/Session semantics and no Claude Desktop mode support.
