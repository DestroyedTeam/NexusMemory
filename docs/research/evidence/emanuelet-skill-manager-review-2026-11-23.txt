## Capability boundary against Nexus Memory

This is a fairly feature-rich **Skills manager**, not a cross-Harness memory/session migrator. It has a canonical local Skill store, source repositories, dependency/profile/project `.skills.json` declarations, Claude Code `SessionStart` activation hooks, search/usage analytics, Codex/OpenCode shared Skill deployment, and an MCP server that exposes this manager's Skill operations. `sm mcp setup` registers the manager's own server in Claude Code and Codex CLI; it does not transfer arbitrary existing MCP configurations. Bifrost support synchronizes Skills, not conversations or memory.

No ChatGPT/Codex Project or Section/Section Group model, Session events/forks/parent-child graph, transcript/turn chronology, attachment or token/cost transfer, plugin transfer, scheduled-task transfer, or native Claude Desktop third-party-gateway Chat/Cowork/Code or local Claude Code conversation importer/exporter was found. `.skills.json` is a list of project resources, not native Harness Projects or session trees; `SessionStart` is a trigger for Skill activation, not SessionGraph migration. The README targets Claude Code, Codex CLI, and OpenCode; it documents macOS/Linux (elsewhere says Linux only), not Windows.

Keep only as adjacent resource-plane design reference: canonical Skill storage, dependency/profile manifests, atomic symlink replacement that refuses real-file collisions, version history, MCP-backed Skill discovery, and Bifrost Skill sync. The automatic importer must not be used against real user state until its loss/boundary issues below are fixed and tested.

## Synthetic-only data-loss and read-boundary probes

All fixtures used disposable `/tmp` homes, not the host's real `~/.claude`, `~/.agents`, Codex, or MCP state.

1. **Duplicate content drops distinct Skill resources.** Created same-slug `shared-skill` directories in synthetic `.claude/skills` and `.agents/skills`, with byte-identical `SKILL.md` but distinct `references/CLAUDE_ONLY_REFERENCE.md` and `references/AGENTS_ONLY_REFERENCE.md`. Invoked the built actual CLI: `SM_TEST_HOME=/tmp/nm-sm165-poc/home node dist/bin/sm.js list`; exit 0, stdout began `ℹ Auto-adopted 2 skill(s): shared-skill, shared-skill`. Both source directories were deleted. The canonical store contained the Claude reference only; `AGENTS_ONLY_REFERENCE.md` was absent, with no backup. In `autoAdopt()`, the duplicate path compares only SKILL.md content hashes and removes the original directory on a match, before the extra-file copy used for a newly imported skill. Existing tests check one directory's references but do not test merging distinct assets across duplicate copies.
2. **Nested SKILL.md symlink reads outside the tool root.** Created synthetic `.claude/skills/symlink-skill/SKILL.md` as a symlink to `/tmp/nm-sm165-symlink/outside-sentinel.md`. The actual CLI exited 0 and printed `ℹ Auto-adopted 1 skill(s): symlink-skill`; observed `source_directory_exists False`, `external_target_exists True`, `external_sentinel_imported_to_canonical True`. `detectUnmanaged()` skips a symlink only at the direct tool-directory entry; `findSkillFileInDir()` follows a nested SKILL.md symlink via `pathExists`/`readFile`, then auto-adoption imports its external contents and removes the containing directory/link.
3. **Implicit mutation on read/tool calls.** The CLI pre-action hook auto-adopts before normal commands (except completion/MCP/TUI/dry-run); MCP `withToolHandler()` silently calls `autoAdopt()` before every MCP tool invocation. `autoAdopt` is enabled by default. The README documents scanning on each CLI/MCP operation and removal of original files/directories, but the synthetic duplicate-assets case demonstrates that the documented background action can discard non-SKILL resources. A read/list/search call can therefore mutate source directories.

These are reproducible code/data-loss and local read-boundary defects, not claims about remote execution. Do not use auto-adopt on user state as a migration transaction until it is opt-in/previewed, merges or backs up all assets, and does not follow nested symlinks.
