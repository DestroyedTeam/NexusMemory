## Disposition

**Exclude as a Nexus Project/Section/Session migration engine. Keep only as a low-confidence adjacent Skill `ResourcePlane` / target-directory inventory idea. Do not reuse its installer or claim its behavior is source-audited.** The public repo is a docs/catalog/skill package; the published executable comes from a private SourceLink repository that is unavailable from public refs. Static decompilation of the published NuGet app reveals a possible destructive overwrite path that merits maintainer clarification and an isolated runtime test before any adoption.

## Published package provenance and static decompilation

- The NuGet 0.4.0 package was downloaded to `/tmp/nm-spm-package-review-2026-11-21/spm.0.4.0.nupkg` and inspected as a ZIP without executing the application. It contains `spm.dll`, `Spm.Core.dll`, PDBs, dependencies, and a package signature, but no source or tests. The `.nuspec` repository commit is `742a52dcd9a0eaa02d45505a7dac9341e79652f3`.
- The embedded portable PDB SourceLink points to `hiadamhere/skills-package-manager-private` at that commit (`https://raw.githubusercontent.com/hiadamhere/skills-package-manager-private/742a52dcd9a0eaa02d45505a7dac9341e79652f3/*`). The repository/source URL returns 404 anonymously. The current public repo refs are `main`=`ca8d684e...` and tag `v0.4.0`=`0d3122e...`; `git cat-file` cannot resolve the npm/NuGet `gitHead` `742a52d...`. Thus the shipped executable's exact source is not present in the public source repository; this is a provenance/reproducibility gap, not evidence of malicious behavior.
- As a limited independent implementation inspection, official ILSpyCmd 9.1.0.7988 was installed under `/tmp` only and used through the available .NET 8 host to decompile the shipped `spm.dll` and `Spm.Core.dll`. No SPM executable was run. The decompiler emitted incomplete/unknown-IL annotations for some .NET 10-generated code; these notes are static reconstructed evidence, not original source or a runtime proof.
- Decompiled structure confirms one `Installed` dictionary record keyed by skill name, with one `ProjectPath`; the README itself documents that installing one same-name Skill in multiple projects tracks only the most recent path. `Agents.Plan` computes the shared canonical `.agents/skills` directory plus per-agent directories. The MCP surface is the manager's own search/list/info/install/catalog tooling; no ChatGPT Project/Section/session reader, transcript serializer, branch/child-task graph, media converter, MCP config/plugin importer, memory or schedule transfer was found.
- **Static destructive-write concern:** in link mode `DeployScope` calls `ForceDeleteDir` when a target agent's Skill path already exists as a real directory, then attempts a link (and falls back to `DeployFolder`). `Agents.Plan` constructs that destination without an ownership marker/real-folder conflict gate. `DeployFolder` stages the new tree, moves an existing destination to `.spm-old-*`, then deletes that old tree in `finally` after successful replacement. This means a same-name real/untracked directory can be replaced; this control flow was observed in the decompiled 0.4.0 package but was not runtime-reproduced, so treat as a **high-priority static risk**, not a reproduced exploit. `Hygiene.Inspect` is more conservative for cleanup (untracked folders are reported and not eligible for delete), but that does not guard the install/replace path. Do not install over real user directories without upstream source clarification, a conflict preview, and a sandboxed behavior test.
- Positive but adjacent patterns: skill source commit tracking; separate shared asset and target-folder projections; project/global scope; configuration write via temp-file + overwrite rename; process invocation uses `ArgumentList` with shell execution disabled; cleanup findings/quarantine concepts. These are not equivalent to a portable conversation/session snapshot and cannot be adopted without source-level verification and safety tests.
