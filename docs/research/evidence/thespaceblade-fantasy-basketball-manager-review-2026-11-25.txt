What it does / where it connects
- Python CLI exposes reads, projections, free-agent ranking, and roster mutations. Optional stdio MCP server exposes the same workflows; Skills instructions are in `skills/fantasy-basketball-manager/SKILL.md`. The Skill is copy-installed into a compatible agent skills directory; no project/session import/export or source/target adapters exist.
- Requests are delegated to `npx -y api-anything@0.4.0` and an API Anything local saved session; the README requires a local Chrome login window and says no ESPN API key is required. That is a local browser/session-cookie integration, not an API-key Claude Desktop gateway. No account, saved session, credentials, or ESPN data were opened during review.

Positive MCP side-effect design prior art
- MCP writes are absent by default: `create_server(..., allow_writes=False)` registers `fantasy_apply` only when the server is started with `--allow-writes`; the offline optional-dependency test verifies this. Other tools are reads or previews.
- Write workflow fetches fresh snapshot/calendar/lineup, checks period/limits/roster/waiver/lock constraints, asks the backend for a dry preview, validates the exact HTTPS ESPN host/path/body/players/slots, and sends only with `--apply`. It writes an intent record before sending, records the response, reads back actual roster/lineup state, and refuses automatic retry after ambiguous sends. Tests cover preview-no-send, one send + readback, uncertain-send no retry, waivers, locked players, mismatched preview and slot/capacity constraints.
- Caveat: the MCP permission gate is server-wide, not a per-call human confirmation. The MCP tool docstring says “explicitly user-authorized”, but once `--allow-writes` exposes `fantasy_apply`, the code itself accepts the tool call and invokes `--apply`; authorization is a prompt/host policy.

Security and data-handling finding (synthetic only)
- The transaction journal records operation and arguments before send and after readback. A synthetic probe using fake HOME/config directories mode 0755 and umask 022 wrote a fabricated player-ID marker to `transactions.local.jsonl` mode 0644. The code uses ordinary `mkdir`/`open('a')` with no explicit chmod. If the user's home/config parent is traversable, local roster/action metadata may be readable by other local users; enforce 0700 directories and 0600 files. No real ID, credential, or session was used.
- `Client.run` calls the external API Anything CLI via `npx`, pins version 0.4.0, captures stdout/stderr and avoids echoing request body, headers, or session data in backend errors. Session cookies stay in API Anything's separate local store. Project README warns never to paste cookies or publish captured sessions.
