SUMMARY / DISPOSITION
Zeppeli is a local-first AI coding-agent CLI with local Ollama and OpenAI-compatible cloud/self-hosted inference through LiteLLM. It records its own process-local sessions, a structured history JSON and a separate append-only event log. It is not a cross-Harness importer/exporter: there are no source adapters, destination writers, file import, archive export, session resume/restore, ChatGPT Projects/Sections, Claude Desktop third-party-gateway Chat/Cowork/Code surfaces, or Destruction Era project graph. Retain as a valuable native local-history/event schema reference, not as a migration implementation.

NATIVE SESSION / EVENT DATA MODEL
- Every process creates one new UUID/session; it writes ~/.zeppeli/sessions/session-<first-8-UUID-chars>.json and ~/.zeppeli/logs/log-<full-UUID>.jsonl. No session reader/restore path is implemented; docs explicitly say a restarted process begins a fresh session and cannot recover prior context.
- Version-1 JSON fields: id, cwd, title (cwd basename), createdAt/updatedAt, provider, model, ollamaUrl/lmStudioUrl, history[], runs[]. History roles are user/assistant/tool with content and a persistence timestamp; tool calls/results are paired in the history. Runs carry UUID, timestamps, running/completed/failed state and usage statistics (duration, hop count, tool calls, input/output tokens when available). The run array is a flat sequence within one process session, not a parent/child task graph or branch tree.
- SystemMessage is deliberately skipped from history. Session history conversion reduces multimodal message content through extract_text(), which keeps only text blocks. A synthetic probe with a fake data-URL image confirmed that only "inspect this image" is stored and the image bytes are not. No attachment payload/checksum registry exists.
- core/eventlog.py writes separate events (session_started, run_started, model_activity, run_completed, cli_error). A run event includes a 200-character prompt preview, full answer, per-hop model activity, full untruncated tool outputs and (when supported by local Ollama) raw reasoning_content. Files are plain JSON/JSONL under the user's home directory; no encryption, retention policy, redaction layer, or cross-file manifest was observed. Thus this is rich, sensitive local diagnostic state, not a portable/sanitized interchange archive.
- Session metadata declares provider as "ollama" unconditionally even when CLI flags configure a cloud/self-hosted LiteLLM endpoint; model is saved, but the base URL and API key are omitted. This prevents reconstructing the actual cloud provider/gateway deployment from the session while also avoiding key persistence.
- Project identity is only cwd and derived title; there is no Project/Section/Section Group object, session-to-project membership table, branch/fork ancestry, MCP/plugin manifest, scheduler, or memory snapshot. Skills are read from ~/.zeppeli/skills/ and <cwd>/.zeppeli/skills/; skills/system instructions are not included in session history. Slack threads are keyed in an in-memory ThreadRegistry; thread mapping/context clears at process restart even though local session/event files remain. The Slack bot is an integration, not a general plugin/migration plane.
- One synthetic probe: append_history_from_messages() on a user content list containing text plus a fabricated image data URL produced one history entry with content "inspect this image"; IMAGE_PAYLOAD_PERSISTED=False; system instructions were also omitted. No real image or user content was used.

COMPATIBILITY / DESIGN VALUE
- Useful concepts: separate resumable-ish conversation history from a more granular append-only run/event ledger; preserve full tool outputs even where model-visible tool output is truncated; explicit run status/stats; FIFO/nonblocking persistence; provenance about cwd/model; tests for serialization/atomic writes.
- Required gaps for Nexus: external-source schema adapters, stable full source IDs, typed multimodal/attachment references and content hashes, Project/Section/task/branch graph, provider endpoint provenance (without persisting secrets), session resume/reopen semantics, retention/security controls, and target-native import/export/verification. Its own schema is not a standard and does not demonstrate migration accuracy.
