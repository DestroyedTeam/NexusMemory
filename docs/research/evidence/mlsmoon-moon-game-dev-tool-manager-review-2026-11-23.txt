## Source-level findings
- `SkillInstaller.InstallAsync` obtains a repo cache, calls `ResolveSource`, then routes ordinary Skills to `SkillCopyInstall.InstallAsync`.
- `CatalogStore.Ingest` fills missing ID/InstallName but does not validate or constrain either path-like value. `MlsmoonSkillConfig.ResolveInstallDirectory` falls back to `WorkspaceScanner.SkillInstallPath`, which simply combines `<workspace>/<root>/skills/<installName>` without checking containment. This is reachable from the catalog `id` in `SkillCopyInstall.InstallAsync`.
- `SkillCopy.Replace` rejects a destination that is already a Git repo, but otherwise recursively deletes an existing destination directory and copies into it without requiring a MlsMoon ownership marker. This conflicts with README's assurance that unlisted local files are not modified/deleted and with its later statement that only marker-bearing directories are deleted.
- `SkillInstaller.ResolveSource` applies `Path.GetFullPath(cache + sourcePath)` but does not require the resolved directory to remain under the cloned cache. A catalog-controlled `sourcePath` can therefore select a sibling/ancestor path if present.
- Plugin/Package destinations are better constrained: `ProjectCopy.ResolveDestination` rejects rooted paths and `.`/`..` segments, canonicalizes the full destination, and checks it remains below the workspace. Preserve this as a positive narrow guard; it does not cover ordinary Skills.
- Marked uninstall checks `.mlsmoon-skill.json` / plugin/package markers, which is safer than the install replacement behavior. The test suite does not cover an unmarked ordinary Skill destination collision or Skill install-name containment.
