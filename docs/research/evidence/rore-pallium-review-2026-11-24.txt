## What it actually does

Pallium is a local single-user coordination/history layer around already running coding agents, not an agent runtime or session manager. README says supported integrations are Claude Code, Codex, OpenCode, and Hermes Desktop/TUI. Relay stores bounded plain-text messages before delivery and may wake a recipient on qualified hosts. It does not coordinate tasks or build a durable task graph. Session History captures selected user/assistant turns from supported integrations and offers broad topic search, exact work-reference search, and bounded nearby-message expansion; optional derived memory is off by default and does not require an LLM for source-only retrieval.

The inspected `storage.sqlite_schema.SourceItemRecord` is a turn/source-item row with source type/id, content type/text, optional metadata/time/role, container/thread/source refs, artifact kind, visibility, agent/use-case, thread position, source-turn ID, relay attribution, processing/forgetting fields. `RelayMessageRecord` stores a sender runtime/session, recipient selector, container, plaintext payload, optional `in_reply_to`, and expiry. Neither is a canonical Project/Section/Conversation/Session/Message/Fork graph. There are no first-class project/section IDs, parent/branch/fork edges, attachment blobs, token usage, user interruption/continuation events, or model/tool execution trace in the History contract. Its `metadata_json` can carry caller-defined opaque values, but there is no ChatGPT importer/mapper or Claude Desktop writer that would populate/reconstruct those values. The docs explicitly say History is not every tool event, a full audit log, proof of live state, or cross-user authorization.

## Fit to Nexus Memory

**Disposition: high-value prior art for local selected-turn retrieval, visibility, provenance and forgetting; not a migration adapter and not a dependency recommendation.** It could inform a separate searchable-memory plane after a canonical archive exists, provided Nexus keeps raw evidence and source identity and does not treat search as fidelity.

No ChatGPT export reader, Codex/ChatGPT Project or sidebar Section Group importer, complete session lineage serializer, resource/attachment transfer, or target writer for Claude Desktop third-party-inference Chat, Cowork, or Code is present. It also does not write local/self-hosted Claude Code transcripts or configure `ANTHROPIC_BASE_URL`/gateway credentials. “Hermes Desktop/TUI” integration does not mean Claude Desktop modes. All three Claude Desktop modes remain in the user's scope, but Pallium cannot migrate any of them.

## Relevant current Claude target evidence checked alongside this candidate

Anthropic's current Claude Desktop on 3P documentation describes a deployment where all model inference is routed through the configured provider and the full Chat/Cowork/Code experience is provided with conversations stored locally (except Code sessions over SSH, which also store on the remote host). The feature matrix says 3P conversation history is on-device, with no Anthropic-cloud sessions or mobile/web access. This is distinct from local Claude Code CLI/API-key use and from Anthropic-hosted Cloud sessions.

The official Claude Desktop import wizard documented here accepts claude.ai conversation/project exports plus local Cowork/Code sessions (and Claude Desktop exports/folders), not a generic ChatGPT/Codex archive. Import is a copy; project instructions may require acceptance; artifacts can be reduced to final outputs; member exports omit project-knowledge file contents and conversation-attachment contents. The 3P local data docs distinguish storage: Chat/Cowork JSON session records and `audit.jsonl` under `local-agent-mode-sessions/`, with uploaded/output files in working dirs; Code session records under `claude-code-sessions/` with transcripts in Claude Code's `~/.claude/projects/`; UI state is elsewhere. Therefore adapter tests must be mode-specific even though inference uses one configured gateway.
