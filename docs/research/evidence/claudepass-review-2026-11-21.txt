WHAT IT ACTUALLY DOES
- `cpass` is a local encrypted secret manager. Secrets live in a single encrypted Vault and are addressed by opaque hierarchical Handles; project `.claudepass.toml` and Global Manifest store only Handle/binding references. The Vault uses a random data key wrapped by the unlock key; XChaCha20-Poly1305 protects both layers. The README/SECURITY describe restrictive filesystem modes, atomic writes, and a one-generation encrypted `.bak`.
- `cpass run` resolves Handles and injects them into one child process (environment or temporary file), redacts known encodings from that child’s stdout/stderr, and applies a heuristic Command Policy. `capture` stores generated stdout; `import` ingests dotenv; `intercept`/`exposed` track prompt-pasted values.
- Targets: Claude Code plugin (UserPromptSubmit Intercept + Bash PreToolUse policy hooks + Skill under `~/.claude/skills/claudepass`), Codex delimited `AGENTS.md` snippet, and an MCP stdio server with `list_handles`, `run_with_secrets`, and `capture`; `integrate mcp` prints a config snippet. This is a Secret/resource plane, not an export/import/archive plane.
- Source/CLI inventory and a targeted search of `cmd/`, `internal/`, `plugins/`, and PRD found no Session, message, branch/subtask, transcript, Project, Section Group, attachment, usage/token ledger, scheduled-task, memory, or conversation import/export implementation. `.claudepass.toml` is a secret-handle manifest, not a ChatGPT/Claude Project.
- There is no per-Secret/per-Agent/per-Session ACL: any process running as the Vault-owning user can request any Handle. Two local agents sharing the same account/Vault share all secrets. The project explicitly excludes cross-machine/team sync, automatic rotation, cloud-hosted sessions and the relay they would need, and Windows support beyond 'it builds'. The Windows Broker is a stub returning unsupported; only `CPASS_KEY` unlock works there.

MODE-SPECIFIC FIT (user confirmed all Claude Desktop modes are in scope)
- Claude Code local CLI: direct supported integration is a local filesystem plugin (hooks + skill); `integrate claude` only writes its own files to the local skills directory. Local Desktop Code tab may share local Code plugins/settings according to Anthropic’s current docs, but this repository does not test the Desktop app or third-party gateway session path.
- Chat / Cowork: this repository has no account-backed plugin uploader/sync or session importer. The plugin support matrix says Skills load on Chat, Hooks are ignored there, while Cowork loads Hooks and local MCP only when the session runs on the computer. Therefore even installing the folder manually would not make Chat’s Intercept/Command Policy hooks function; do not infer full three-mode protection from sharing a plugin manifest.
- Cloud-hosted sessions: explicitly out of scope. The Vault stays on the local machine and is never synced/relayed to a remote sandbox. `cpass run -- <command>` might keep a local API key out of prompt text for a child CLI process, but this is not a third-party gateway configurator, Desktop session adapter, or history migrator.

SECURITY / LIMITS
- Positive patterns: opaque references rather than values in context; local encrypted Vault; project-vs-global declarations; user-owned local process boundary; no telemetry/network relay; exact command wrapper and testable output boundary.
- The docs candidly state redaction is not a sandbox or guarantee: a secret emitted in <4-byte chunks separated by >100 ms can evade the streaming matcher; custom encodings/compression/encryption are not covered; child writes to files/sockets/other processes are invisible; a value split across stdout and stderr is not matched. Command Policy is a known-pattern list, not an authorization system.
- No cloud relay means no remote session access to local secrets. Windows threat claims are not exercised. This matters for a gateway/client deployment and multi-agent/session isolation; do not carry over its same-user, all-Handles policy as Nexus Memory’s authorization design.

FIT / RECOMMENDATION
- Retain as a high-value SecretPlane/security reference and as evidence that secret handoff must be modeled separately from conversation history. It does not move a user’s ChatGPT/Codex Projects, Section Groups, sessions, or artifacts to Claude/Claude Code; it does not handle Claude Desktop Chat/Cowork/Code session hierarchies or third-party API-key gateway state.
- Design takeaway for Nexus Memory: model secrets as opt-in `SecretReference` resources separate from `ConversationArtifact`; keep raw values out of transferable archives by default; enforce explicit project/session scope and per-destination policy instead of a global same-user Vault; treat local vs remote execution as separate capabilities; test each Desktop mode and its component support separately.
- Do not vendor this as a migration engine or assume redaction/Command Policy gives sandbox-level or per-session authorization.
