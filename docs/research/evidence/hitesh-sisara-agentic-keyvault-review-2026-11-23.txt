## Disposition

**Reject as a Project/Section/Session migration product. Retain as a separate SecretPlane architecture reference only.** The repo is a self-hosted Cloudflare Workers + D1 store for API keys, tokens, and environment variables, with a CLI and stdio MCP server. Its “Project” is a credential namespace with optional GitHub repo binding, not a ChatGPT/Codex Project or Section, and there is no conversation/session/transcript/branch/media/schedule import/export schema. It does not migrate Skills, MCP server definitions, plugins, user memory, or any Claude Desktop Chat/Cowork/Code or local/self-hosted Claude Code conversation data. A credential store or MCP API is not evidence of Harness configuration migration.

For Nexus, keep secret values outside the portable session bundle. At most transport an opaque credential locator plus required scope/provider metadata and a `reauthorization_required` state; resolve or relink secrets at the destination only after explicit user action. This separation applies to the confirmed Claude Desktop third-party-gateway Chat, Cowork, and Code tracks and local/self-hosted Claude Code as well as other Harnesses.

## Source and implementation review

- README describes Projects as groups of secrets, optional repo-origin binding, versioned writes, and rotation. The API/MCP can deliberately retrieve plaintext secret values. CLI supports pulling values into local `.env`; this does not preserve conversation context.
- `docs/ARCHITECTURE.md` specifies D1 plus AES-256-GCM envelope encryption: fresh random 256-bit DEK per version, wrapped with a 256-bit KEK stored as a Worker secret. The design explicitly is server-decryptable, not zero-knowledge: MCP/CLI need plaintext; a Worker runtime compromise exposes the active key material. Tokens are opaque, peppered HMAC hashes; project-scoped read-only/read-write tokens and expiry/revocation are supported. KEK backup is mandatory for recovery.
- Source reviewed: `packages/worker/src/secret-service.ts`, `src/crypto.ts`, `src/auth.ts`, `src/routes/secrets.ts`, `src/routes/tokens.ts`, D1 migrations, `packages/mcp/src/index.ts`, tests, `cli-go`, and package manifests. Secret history is append-only and audit events record operations; MCP `get_secret` returns plaintext to an authorized caller. Least-privilege, project-scoped read-only tokens are the safer default for agents.
- The worker validates the writer's token against `body.projectId`, but `resolveRepoId()` returns a supplied `repoId` unchanged (or resolves an origin globally) without checking that the repo belongs to that same project. The schema has separate foreign keys from `secrets.project_id` to `projects.id` and `secrets.repo_id` to `repos.id`, but no composite project/repo constraint.

## Synthetic scope-consistency probe

The request returned HTTP 201 and the persisted response retained `project_id=A` and `repo_id=B_repo`; the additional test passed. The value was the literal synthetic string `not-a-real-secret`. This confirms cross-project repo association is accepted (an integrity/misbinding validation gap); it **does not demonstrate** that a B-scoped token can read A's secret or that this is a cross-project confidentiality bypass. Read/export handlers also filter by the secret's project.
