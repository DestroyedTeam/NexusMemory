Its README says it is a Rust reimplementation of OpenAgentsControl v0.7.1; the vendored `content/` directory is compile-time embedded and maintained locally. ## Disposable symlink-containment probes (critical writer/removal gap)

The normal happy-path tests do not cover symlinked managed parents. `plan_files` joins embedded registry paths directly under the caller's `--dir`; `copy_bytes` uses `create_dir_all`/`fs::write` without resolving and constraining symlinks. `add_component` then hashes every planned target into the manifest, even when `copy_bytes` reported a collision instead of writing that target. `remove_component` trusts that manifest path and uses `remove_file` before pruning directories.

1. **Install escaped the chosen tree.** Synthetic temp layout: managed root `/tmp/nm-myagentcontrol-followup210/symlink-write/managed`, with its `config` subdirectory a symlink to sibling `/tmp/nm-myagentcontrol-followup210/symlink-write/outside`. CLI `add config:agent-metadata --dir <managed>` exited 0 and reported one file copied. It created `outside/agent-metadata.json` (10,292 bytes, SHA-256 `c7ae34cb341f14e742d277772933946678b41389ee379755b29c6c87ba7e737c`) outside the requested managed root. The package's own `.mac/manifest.json` was written under the managed root.
2. **Remove deleted a foreign sentinel despite a collision and then errored.** Separate temp layout had the same symlink but prepopulated the outside `agent-metadata.json` with `SYNTHETIC_FOREIGN_OWNER_CONTENT`. `add ...` without `--force` exited 0 and reported `0 file(s) copied, 0 skipped, 1 collision(s)`, yet wrote the foreign file's SHA-256 into its manifest entry (`655ef7106a0d10b72b2b910646dc6379a620fb0972ed944ba6b48a97f07ac5d3`). `remove config:agent-metadata --dir <managed>` exited 1 with literal stdout/stderr combined by the runner: `Error: E600: cannot remove /tmp/nm-myagentcontrol-followup210/symlink-delete/managed/config: Not a directory (os error 20)`. After that failed command, the outside sentinel file was gone while the `managed/config` symlink remained. Thus the command can cause an outside-root deletion and partially fail after the destructive action.

These are genuine source-code-path observations using synthetic temp files only. A production-safe resource adapter would need canonical containment after symlink resolution for every planned/read/write/delete target, must never claim manifest ownership of a collided unowned file, and must stage/rollback the whole write transaction. The candidate's hash manifest and collision-aware default are useful concepts but insufficient as implemented.
