## What the code actually installs

- `agentskills add` parses local paths or GitHub handles, shallow-clones a branch/tag, copies one skill or all discovered `SKILL.md` folders, and writes `~/.agents/skills` or project `.agents/skills`. The lockfile is `.agents/.skill-lock.json` v3; it records source repository, source URL, skill path, folder hash and timestamps.
- `detect_agents` recognizes marker directories for Cursor, Claude Code, Codex, Copilot, Amp, Cline, Continue and Kiro, and `add` prints the first detected name. But `installer.rs` ignores that detected agent and always writes `.agents/skills`; `AgentInfo.skills_dir` is display metadata, not a per-target serializer. This is a shared directory convention, not eight verified native adapters.
- Current official docs validate `.agents/skills` for Codex, Cursor and Copilot; OpenCode V2 also recognizes it as a compatibility path. Current Claude Code docs specify `.claude/skills` and do not list `.agents/skills`. Thus the README's detection list cannot be counted as eight working targets without host-specific runtime tests. Claude Desktop Chat/Cowork session stores, account skills, Code session records, MCP, plugin, Project, Section, memory and schedule conversion are absent.
- The `SkillSource` records a `git_ref` while fetching, but `SkillLockEntry` omits that ref/commit. `update` reconstructs `owner/repo@skill` and fetches the default `main` branch, so a one-time pinned ref is not a reproducible lock. The SHA-256 folder hash excludes dotfiles and concatenates relative path bytes with file contents without delimiters/lengths.

## Reproduced isolated behavior/security probes

1. **Remove escapes the skills root.** First attempt lacked the intermediate `.agents/skills` directory and therefore returned exit 1 (`Skill '../../../victim' not found in project scope.`); the temporary victim remained. After creating that directory, `agentskills remove ../../../victim` resolved to a sibling of the project root, exited 0, printed `ℹ Removing skill '../../../victim'...` and `⚠ Removed '../../../victim' directory but it was not in the lockfile.`, and deleted the temp-only victim sentinel. The checked path was `/private/var/folders/62/8__6fhqd5dq7bh2cgp2_75lh0000gn/T/nm-kayaman-remove-path-probe-297vm8hk/victim`; the entire temp tree was automatically removed afterward.
2. **Failed replacement deletes the old skill and leaves stale lock.** Initial local install of `demo` exited 0 and wrote `# old`. Re-run with a changed skill plus a dangling symlink in the source exited 1 (`✗ No such file or directory (os error 2)`) after `install_single` removed the existing destination. The old `SKILL.md` was gone, the destination was absent, and `.skill-lock.json` was unchanged. All paths were under disposable `/tmp/nm-kayaman-overwrite-probe-cbzouttr/`.
3. **Dotfiles are copied but omitted from integrity hash.** Two temp skills with identical `SKILL.md` but different `.private` contents both installed successfully and received the same lock hash `b8076aef1d6e7fff009d97a39f8d9e581483c133dbf0848fb47f9c20cb3d972d`.
4. **Hash framing collision.** Two temp skill trees with identical `SKILL.md` but distinct files (`a` containing `bc` vs `ab` containing `c`) both installed successfully and received hash `1971e4d30c53a0f541391a8f6861bb674307eaa3a3f98013a1cce4e146a12f3e`. Inference from `update.rs`: because updates compare this same hash, such distinct trees can be treated as unchanged.

## Disposition

Retain the open `SKILL.md` package/source idea and lockfile/provenance vocabulary as a narrow ResourcePlane reference. Do not adopt its installer, path handling, update/rollback semantics, lock hash, or treat its 8-marker detection as 8 complete cross-harness adapters. It has no SessionGraph or ChatGPT/Claude Desktop migration support, and its reproduced path traversal plus destructive failed update are direct blockers for reusing mutation code.
