## Product model / what it actually transfers

Grimoire (`grim`) is a pre-1.0 package manager for **agent configuration assets**. It declares Skills, Rules, Agents, MCP servers, Hooks, Settings and Bundles in `grimoire.toml`, resolves/pins registry content in `grimoire.lock`, and renders each artifact into client-native paths/config formats. `LockedArtifact` records a name/kind, pinned OCI identifier or local path+SHA-256, bundle provenance and dependency edges; it is not a conversation/session model. The resolver and install record use digests, client scopes and file/config footprints.

Its published compatibility matrix is explicit and nuanced: Claude Code, Codex, Copilot, Cursor, Gemini, Zed, Amp, Kiro, Junie, OpenCode and other coding clients have per-artifact support/degraded/declined cells. It may refuse a transformation rather than write a file the client ignores. A separate marketplace guide documents distribution of plugin artifacts to ChatGPT/Codex and the Claude Desktop Chat/Cowork UI, but this is repository/plugin packaging—not ChatGPT Project or conversation import. ChatGPT's desktop app reads a local `.agents/plugins/marketplace.json` or an administrator imports a GitHub marketplace. The official OpenAI help article says marketplace sync imports plugin content, not member accounts or app access.

The Grimoire compatibility matrix's “Claude” target is Claude Code (`code.claude.com`), not a distinct Claude Desktop Chat/Cowork/Code session adapter. Grimoire's separate marketplace guide documents a Chat/Cowork marketplace route; it does not establish a generic Desktop session store/import path. Anthropic's current help article says plugin sync into Claude Code requires signing into a Claude account; plugins do **not** sync when Claude Code is using API-key authentication or a cloud provider. It distinguishes plugin assets from chat history. It also states local MCP servers run in Cowork and Claude Code, not Chat. Therefore, do not imply that Grimoire migrates API-key-mode sessions or conversation history into any of the three Desktop modes.

No ChatGPT/Codex Projects, Sections/Section Groups, transcript/session tree, user/assistant/tool turns, interruption/fork lineage, files/images/links, token/cost history, project memory, scheduled conversations or cloud-session import/export model was found in the reviewed manifest/lock/install/export/MCP surfaces. Its `project` means a config/working-directory scope used for installing assets, not a hosted conversation Project; plugin `project` export renders a locked asset set, not a ChatGPT/Codex Project archive.

## MCP / Skills / plugin boundary

- The tool registers a canonical MCP descriptor into host-native JSON/TOML configuration and supports client-specific formats/declines. Its staging/export code can package a project's locked assets into Claude plugin and Agent Plugins (Codex) layouts. This is valuable **asset distribution**, not the ability to read arbitrary existing MCP server entries or conversation sessions back into Nexus.
- A synthetic local path Skill (`skills/demo-skill/SKILL.md`) was installed in isolated project scope to Claude and Codex. Grimoire wrote a SHA-256 path pin to `grimoire.lock`; the identical Skill bytes appeared at `.claude/skills/demo-skill/SKILL.md` and `.agents/skills/demo-skill/SKILL.md` (Codex's shared Agent Skills pool).
- `grim export plugin --project` then generated separate Claude and Codex plugin trees, each carrying `demo-skill/SKILL.md` with the same digest and client-specific manifests. This is a real, synthetic local packaging probe; no external registry, account, model, user Skill or session was used.
- A local `grim add ./mcp/demo-server.toml --kind mcp` probe exited 64 with `path sources are not supported for mcp artifacts`; no client config was written. A remote/OCI MCP artifact can be consumed and rendered, but this tool path does not import arbitrary local MCP config. No AI process was started during any probe.
- Official Claude Help says Claude plugins may bundle Skills, connectors and sub-agents. In Cowork and Claude Code they can also include hooks and local MCP servers; in Chat, hooks/sub-agents/local MCP are not active. For Claude Code, sync from Claude account does not occur under API-key or cloud-provider authentication. OpenAI's workspace marketplace import instead syncs plugin packages from GitHub and does not connect member accounts or grant app access.

## Safety / use as a reference

Grimoire has a digest lock, staged rendering, per-client capability matrix, non-destructive conflict checks/force flags, content-drift status and explicit hook consent state. These are useful Nexus patterns. However, MCP descriptors contain executable commands/URLs and hook artifacts can control agent actions: importing them must be previewed, provenance-checked and separately approved. Claude's own docs warn that local MCP servers run with local process permissions; ChatGPT marketplace sync may automatically pick up future repository plugins, so pinning/administrator review matters. Do not invoke imported commands as part of a session import.

## Disposition

Classification: **strong adjacent cross-harness configuration/Skills/MCP/plugin asset package manager; not a Session/Project migrator**. The best pattern to borrow is the typed `artifact → digest lock → per-client capability decision → staged native projection → output drift record` pipeline. Keep the data planes separate: never reinterpret that asset lock or a generated marketplace as a session archive, ChatGPT Project, Claude Desktop mode store, or API-key Cloud conversation. Preserve imported asset commands and hooks as inert data pending human approval.
