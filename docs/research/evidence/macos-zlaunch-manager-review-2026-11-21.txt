## Product boundary

This is a native macOS launchd service GUI + CLI + stdio MCP server. It exposes 19 tools named `launchd_*` to list, inspect, start/stop/restart/load/unload/enable/disable services; read logs/plists; create/delete/write plists; force-reload services; and open its GUI. A local process-level JSON-RPC smoke using only `initialize` and `tools/list` exited 0 and returned exactly those tools; no session/project/chat/transcript import tool appeared. Source/docs contain no ChatGPT/Codex/Multi-Harness session, Project, Section, memory, token/cost, attachment, branch, or scheduled-task data model. This is an OS-service control MCP, not a Harness migrator or a project/session manager.

The README shows a local `claude_desktop_config.json` stdio config and Kiro config. Its Kiro `autoApprove` example includes only read-only tools, which is the prudent boundary. The server itself does not enforce confirmation: `handleToolsCall` dispatches mutating calls directly. Other MCP hosts could grant these tools broader approval. The server is listed for Claude Desktop and Kiro only; the source does not demonstrate support for Claude Desktop Chat, Cowork, and Code separately, or Claude Code local sessions. All three Desktop modes remain separately in user-confirmed scope.

Current first-party Claude Desktop guidance now directs local MCP installs through Desktop Extensions (`.mcpb`) and an in-app extensions UI; it describes a `manifest.json` and `mcpb pack` conversion flow. This repository has no tracked `.mcpb` or `manifest.json`, and its README only gives a raw JSON config example. Do not treat the README snippet as evidence of current extension packaging or session compatibility; raw-config operation was not independently exercised. Official current reference: https://support.claude.com/en/articles/10949351-getting-started-with-local-mcp-servers-on-claude-desktop.

- MCP `ServiceManager.create()` accepts arbitrary `label` if `label.contains(".")`, then writes to `(domainPath(domain) as NSString).appendingPathComponent("\(label).plist")`; there is no path-containment check. The MCP `launchd_create` schema passes the label directly.
- A sandboxed source POC compiled the actual MCP `ServiceManager.swift` with only the `user` LaunchAgents root redirected to `/tmp/nm-zlm-poc/home/Library/LaunchAgents`; `create()` itself was otherwise unchanged. Input `label="../../escaped.poc"` passed its only validation and wrote `/tmp/nm-zlm-poc/home/escaped.poc.plist` outside the intended `LaunchAgents` directory. Exit 0. No launchctl call or user path was touched. This is a confirmed file-path traversal in the MCP `launchd_create` path.
- The MCP server exposes high-impact launchd controls and plist writes without a server-side confirmation/authorization layer. The sample Kiro config narrows auto-approval to read-only tools; do not auto-approve mutators. No real service was started/stopped/created/deleted in this review.
- `requiresPrivilege(_:)` exists in MCP `ServiceManager.swift` but no call path uses it; MCP methods call `launchctl` directly. The README says system operations require root/standard authorization (GUI/CLI paths); MCP privilege behavior for global/system domains was not tested, so current behavior should not be assumed from GUI/CLI docs.
- Local compiled MCP handshake: `initialize` and `tools/list` returned 2 JSON-RPC responses; server advertised protocol `2024-11-05` and 19 launchd tools; process exit 0, no mutating tool invoked.

## Disposition

**Screen as a low-relevance false positive for cross-Harness migration. Exclude from Nexus Memory's migration engine and do not use its MCP `launchd_create` with untrusted labels.** It may be a narrow reference for a local stdio MCP process with distinct read/write tools, but it has no conversation/session/resource-export semantics. Before any MCP reuse, require path-safe label validation, server-side confirmation/least privilege, tests, and current Desktop Extension packaging; keep all system-management tools out of auto-approve lists.
