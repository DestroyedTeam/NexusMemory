## Scope, adapters and packaging

- Strongly scoped ResourcePlane CLI: `lint`, `new` scaffold, `search` an offline bundled registry, `list`, `info`, and install every `SKILL.md` directory from a public GitHub repository tarball. It claims Claude Code, Cursor, Codex and Gemini CLI.
- No Project, Section/Group, Session/Conversation/event tree, branches/subtasks, media/tool-call/token log, MCP, plugins, long-term memory, schedule or source/target session converter exists. It is not a Nexus Memory project/session transfer tool.
- Tool paths are convention-based: `.claude/skills`, `.cursor/skills`, `.codex/skills`, `.gemini/skills`; a separate `~/.skillhub/skills` is only searched into a synthetic `global` list bucket. CLI `install` always writes `<--dir>/<tool-path>` and has no `--global` option; no target agent loads `~/.skillhub/skills` as its native skills directory. Current Codex official install guidance uses `.agents/skills/` and `~/.agents/skills/`; current Gemini guidance recognizes `.gemini/skills/`/`.agents/skills/` and user `~/.gemini/skills/`/`~/.agents/skills/`. Thus Codex and the advertised “global” bucket require correction/validation; Claude Desktop's three modes are not represented.
- Project-level versioning/pinning is explicitly out of scope: install downloads the moving `main` branch, falling back to `master`; no resolved commit hash or lockfile records the content. The offline registry is intentionally small and curated.

## Security result — path escape reproduced safely

- The README claims tar traversal is guarded. `safe_extract_tar` checks each member's lexical `abspath/commonpath`, then calls `tar.extractall(dest)` without validating link targets or specifying an extraction filter. A tar member path itself can be inside `dest` while being reached through a previously extracted symlink to outside `dest`.
- I created a disposable local tar with a symlink `repo-main/payload/link -> ../../../outside` followed by a file `repo-main/payload/link/pwned.txt`, and called the exact `safe_extract_tar` function on a fresh `/tmp` extraction directory. On CPython 3.12.10, the function returned normally and wrote the exact text `proof-in-disposable-temp-only` into the sibling temporary `outside/pwned.txt`. The entire temporary root was removed afterward; no user path was used. Existing `test_safe_extract_blocks_traversal` checks only a direct `../escapee.txt` member and passes, so it misses this symlink/hardlink chain. This is an arbitrary file-write outside the staging directory when installing a malicious skill repository.
- Python's official docs say `tarfile` default extraction changed to `filter='data'` only in Python 3.14; previously extraction behavior was fully trusted. This project explicitly supports Python 3.8+ and CI 3.8/3.11, and its code omits a filter, so the code-level gap is material to supported versions. Do not consider the lexical `commonpath` test sufficient; reject links/special members or use a safe filter/backport and keep extraction dirfd-contained.
- A separate code-level reliability issue: with `--force`, the installer deletes an existing Skill directory before copying its replacement and has no rollback if `shutil.copytree` fails; no failure-injection test covers this path.

## Disposition

Keep as a useful low-cost ResourcePlane reference for offline skill metadata linting, scaffolding and deterministic registry search. Do not reuse its remote tarball installer in production until link-target escape is closed and regression-tested on the oldest supported Python, and make replacement transactional. It has no Project/Session semantics, no current three-mode Claude Desktop target, no actual vendor session import, no MCP/plugin/memory/schedule migration, and no branch pinning. Status: adjacent Skill CLI, not the requested Nexus Memory migrator.
