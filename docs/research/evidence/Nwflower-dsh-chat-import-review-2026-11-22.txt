## Verdict

This is a strong, actively maintained **DSH-native session importer/exporter** and a useful adapter/IR reference. It is not a complete Nexus Memory solution and is not a Claude Desktop 3P Chat/Cowork/Code importer. The ChatGPT path materially restores text history and each root-to-leaf branch as a separate DSH session, with structured tool calls/results when recognizable. However, it does not import ChatGPT Project/Section membership or project assets/instructions/memory, loses non-text attachment content, has no ChatGPT usage/model accounting, and does not retain graph edges between the separately materialized branch sessions. It is therefore a possible temporary bridge to Claude Code only, not a lossless Project/session graph migration backend.

## Pinned implementation facts

`lib/convert/chatgpt.mjs` reads a parsed `conversations.json` array and consults `conv.id`, `conv.title`, `conv.create_time`, `conv.mapping`, node parent/children, message role/time and `content.parts`. It does not read a ChatGPT Project/Section id, project instructions, project files, project memory, `current_node`, model metadata, or token usage. Text extraction accepts strings and objects with a `.text` field; other parts are ignored. The importer returns DSH session IR with provider/model fixed to `chatgpt`, no cwd, and no image conversion.

Branch behavior is explicit: default `branch:"main"` walks the last child until a leaf; `branch:"all"` performs root→leaf DFS and creates one independent DSH session per leaf. Additional paths get a suffixed `sourceId` and branch-marked title, but no stored parent/child edge to the main session. The default main leaf is determined by child order, not a parsed active-node field. The tool-call decoder recognizes JSON-string/object carriers with `tool_name`/`tool_call_id`/`args` (or `name`/`id`) and pairs subsequent `role:"tool"` results FIFO because the export lacks a result-side call id; it marks results `isError:false`. `toolCallCarrier`, `chatgptMessageText`, and `chatgptMessageParts` have no direct unit-test caller according to the pinned CodeGraph index.

The ChatGPT source schema has no cwd, so `finishConversion` cannot recover a workspace from the source. The pinned import guide documents that `workspaceMode:auto` sends missing/unavailable cwd sessions to `$DSH_HOME/dsh-chat-import-workspace`; `workspaceMode:per-project` leaves them ungrouped. This is one shared landing workspace, not ChatGPT Project grouping.

Pinned `docs/INTERCHANGE.md` defines a useful normalized DSH IR with turns/steps, text/reasoning/tool calls/results, optional image bytes, timestamps, provider-reported usage, and compaction. `lib/attachments.mjs` materializes supported image bytes through the host attachment service, with explicit `imagesDegraded` counts and storage limits. The ChatGPT parser does not currently populate the image/usage/model fields, so generic IR capabilities must not be mistaken for ChatGPT-source support.

The plugin can serialize DSH sessions to Claude Code JSONL via `export_chat({format:"claude"})` under `~/.claude/projects/<slug>/<uuid>.jsonl` (or `outputDir`), with fresh UUID and create-if-absent semantics. The exporter requires a cwd from session metadata or explicit args. The ChatGPT importer itself gives no source cwd, and a DSH ChatGPT session defaults to the dedicated import workspace. A caller may specify a target project cwd when exporting, but that is manual mapping, not carried ChatGPT project membership. This route creates a **Claude Code transcript**, not a native Claude Desktop Chat/Cowork session; Desktop 3P stores Chat/Cowork state separately and local Code records separately from the transcript.

There is a pinned-document/runtime mismatch: the `v0.26.2` Usage Guide says that file import can be transferred to another tool through `import_chat`'s `target` parameter. The actual pinned `makeImportChatTool` schema has no `target` property (`COMMON_PARAMS`/`EXTRA_PARAMS` omit it), and `runImportSpec` always runs the DSH importer. A synthetic fake-host call with `target:"claude"`, `cwd`, and `outputDir` still returned `mode:"batch"`, imported one session into fake DSH persistence, and produced no Claude output path. The UI has a separate `transferDiscoveryItem` pipeline; the tool schema claim must not be used as proof of a callable tool-level transfer.

## Synthetic probe (no user export or host data)

Ran `convertChatgptJson` on a synthetic conversation with a placeholder root, one tool call/result, a non-text image-only user turn, two leaf branches, and synthetic `project_id`, `section_id`, and `current_node` fields. Observed two DSH sessions. Both retained the structured tool call/result, but `isError` was false; `cwd` and group metadata were absent; the synthetic project/section fields were absent from results. With `current_node:"a_branch"` but last child `a_main`, the parser treated `a_main` as the unsuffixed/main session and `a_branch` as a suffix branch. The image-only user node was skipped and its following assistant reply was attached as another step to the previous text prompt. This is direct behavior of the synthetic probe, not a claim that every ChatGPT export encodes image-only turns identically.

The separate fake-host import probe called `import_chat` with `target:"claude"`; it observed `declaredTarget:false`, `resultMode:"batch"`, `imported:1`, `persistedSessions:1`, and no transfer result. A separate `export_chat` dry-run on that fake session with an explicit synthetic cwd produced a path under a synthetic Claude projects folder, but wrote nothing. No API key, real ChatGPT file, DSH profile, Claude Desktop store, real `~/.claude` path, or inference endpoint was used.

## Assessment for Nexus Memory

Borrow: adapter separation, the interchange turn/step representation, per-source loss counters, preview-before-write, source fingerprints/idempotent reimport, explicit branch-all support, checksum-verified portable DSH bundle, and a DSH→Claude Code JSONL route.

Do not claim: preservation of ChatGPT Project/Section/group graph, image/file uploads, project memory/instructions, shared-project permissions, active branch identity, model/token usage, schedule state, MCP credentials, or native Claude Desktop Chat/Cowork history. The DSH route has an additional manual-cwd/landing-workspace issue and its pinned `target` docs drift from the actual tool schema.

## Official Claude Desktop 3P/API-key boundary rechecked after user clarification

The current first-party documentation confirms the requested target is specifically *Claude Desktop on third-party inference* when using the local app's Developer Mode/configuration window—not Anthropic-hosted Claude Code Cloud. `Help → Troubleshooting → Enable Developer Mode → Developer → Configure Third-Party Inference…` configures the local app. Gateway static API-key auth uses `inferenceProvider: "gateway"` and `inferenceGatewayApiKey`; the gateway must implement Anthropic Messages API `POST /v1/messages` with streaming and tool use (optional `GET /v1/models`). A generic OpenAI-compatible endpoint needs a translation gateway unless it already exposes that contract. Direct Anthropic API auth is a separate provider using `inferenceAnthropicApiKey`.

The 3P Desktop target does include Chat, Cowork, and Code, but the native objects differ: Chat/Cowork share per-session state/transcript/uploads/outputs/audit under `local-agent-mode-sessions/`; Code metadata is in `claude-code-sessions/`, while the transcript is still under `~/.claude/projects/`. The 3P import wizard imports Claude.ai histories/projects plus local earlier Claude Desktop Cowork/Code sessions; it does not document ChatGPT/Codex exports as input. Claude Code Cloud sessions are a separate claude.ai account/hosted surface and are not available through a third-party gateway/API-key deployment.
