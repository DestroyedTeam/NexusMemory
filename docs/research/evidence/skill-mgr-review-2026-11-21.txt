## Disposition

**Strong, narrowly scoped Skill lifecycle implementation; not a Harness/session migrator.** It is useful as a code-quality reference for a small cross-agent `SkillProvisioner` and CLI support matrix, but not as an implementation for Nexus Memory's requested Project/Section/Session/MCP/plugin/memory migration. Do not adopt its filesystem behavior as-is: two disposable local probes found that installing a local Skill follows a source symlink and copies external file contents into the target, and a same-name install replaces an existing unmanaged directory (including unrelated files) while reporting `updated`. These are observed source behaviors, not speculative path-traversal claims.

## Intended scope and product requirements

- `project/1_requirements.md`, `project/2_design.md`, and `project/3_plan.md` describe a standalone multi-agent **Skill** installer/library: one `SKILL.md` source, shared validation, per-agent install roots, `install/update/uninstall/validate/list/show`, and explicit OS support.
- The requirements explicitly list format conversion, hosted registry, arbitrary Git providers, and agent authentication as non-goals. The only resource models are `SkillMetadata`, `SourceDescriptor`, `MaterializedSource`, `AgentAdapter`, and validation/per-target results.
- The published adapter matrix contains five targets: `claude`, `codex`, `gemini`, `openclaw`, and `orcheo`. It has no ChatGPT or Cursor adapter and no mode-specific Claude Desktop Chat/Cowork/Code integration. A local `~/.claude/skills` path is not evidence of Desktop Session support.
- No conversation/Project/Section/Session/message/branch/subtask model, source transcript importer, target session writer, MCP/plugin migration, long-term memory, attachments/media, token/cost ledger, schedule, or API-key/gateway session handling was found. This cannot meet the requested migration end state.

## Implementation review

- `src/skill_mgr/models.py`: `SkillMetadata` carries AgentSkills frontmatter fields; `SourceDescriptor` only has `kind`, original `ref`, local `path`, GitHub repository and nested subpath. It has no resolved commit/revision/integrity field.
- `src/skill_mgr/sources/github.py`: GitHub shorthand fetches the repository's current default branch and downloads its tarball; archive extraction rejects symlinks/hardlinks and resolved paths escaping the temporary root. The command result retains the original shorthand rather than the resolved branch/commit, so a later run can fetch different content without a provenance record. Unit tests mock HTTP; no live GitHub install was used in this review.
- `src/skill_mgr/validation/skill_md.py`: checks required YAML frontmatter, safe single-segment lowercase name, description, and a small field contract; unknown frontmatter keys are preserved as `extra_fields`. It does not semantically translate Skill behavior between Harnesses.
- `src/skill_mgr/services/skill_manager.py` and `src/skill_mgr/fs.py`: source is validated once and one temp-staged copy is made per target. `atomic_copytree()` uses `shutil.copytree()` defaults (which follow source symlinks), deletes an existing destination tree, then renames the staged tree. Existing non-symlink directories are treated as updates; there is no ownership/provenance marker or conflict confirmation. `remove_tree()` does canonical containment-check the requested uninstall path against the registered target root.
- Inference from this source model and CLI: GitHub shorthand installs are not reproducible pins and the JSON response does not reveal the actual default branch/commit selected. This also falls short of the project requirements' risk mitigation that default-branch behavior be explicit in CLI output.
- The installed `skill-mgr` is a standalone CLI/library, not a daemon or Desktop app. Its root paths are filesystem Skill folders; there is no app-mode routing or session store access.

## Safety probes (synthetic-only)

1. **Local symlink follows source outside the Skill directory.** In `/tmp/nm-skill-mgr-symlink-poc-20261121`, source `external.txt` was a symlink to sibling `outside-canary.txt` containing `SYNTHETIC_CANARY_ONLY`. Installing this local skill to a disposable Codex root exited 0. The installed `external.txt` existed as a regular (not symlink) file and contained exactly `SYNTHETIC_CANARY_ONLY`. Thus `shutil.copytree(..., symlinks=False)` follows a local Skill source symlink; GitHub tarballs are treated differently and the archive extractor rejects links.
2. **Unmanaged same-name directory is replaced.** In `/tmp/nm-skill-mgr-overwrite-poc-20261121`, a pre-existing, manually created skill directory contained `UNMANAGED-SENTINEL.txt=preserve-me`. Running `install` of a different source with the same valid Skill name exited 0 and returned status `updated`; afterward the sentinel was absent and the new source body was present. The destination was inside a disposable home. This shows no install ownership manifest/conflict guard, and `install` can destructively replace a same-name target.

These POCs do not show that remote GitHub archives can escape extraction; the archive path/link checks and mocked negative tests passed. They do show gaps in local-source trust boundaries and target ownership handling. The 100% test coverage figure did not cover these two scenarios.
