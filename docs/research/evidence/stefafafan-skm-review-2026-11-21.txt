ACTUAL PRODUCT / USEFUL DESIGN
- Project/global Skill package manager for GitHub sources only. Commands include init, add, install, update, remove, rename, list, inspect and help. It discovers nested SKILL.md files for repo-wide imports and supports output directories such as .agents/skills or .claude/skills.
- skills.json stores requested Skill source/ref/materialization intent; skills.lock.json records resolved Git commit and content integrity; .skm stores cached Skill files; generated Skill paths support copy/link/wrap. This is a useful narrow resource provenance/lock design, not evidence that Skills are the only cross-Harness portable object.
- There is no Session, Message, Turn, branch/fork, subtask, Project/Section Group, transcript, canonical archive, attachment/image/link/tool-result, token-usage, MCP/plugin, memory, schedule, provider credential or Claude Cloud/API-key domain model. No Claude Code source/target adapter and no Claude Desktop Chat, Cowork, Code or third-party inference session writer.
- Accordingly, the product cannot move the user's Destruction Era structure or conversation state. Skill directory placement is the only nearby overlap.

SOURCE / SAFETY REVIEW
- Source supports strong local validation: canonical Skill names reject dot/dot-dot, path separators, controls and Windows-hostile characters; project outputDir rejects absolute paths and lexical escape from project root; lockfile integrity values are checked against traversal; Git uses execFile argument arrays, detached exact-commit checkout and rejects refs starting with a dash; a symlinked root SKILL.md is rejected before copying.
- Materialization is destructive at the managed name boundary: materializeSkill removes the existing outputDir/canonicalName recursively before copy/link/wrap. The filesystem copy helper also recursively removes its destination. There is no backup/undo or multi-Skill transaction journal.
- A sandboxed temporary POC found a real parent-symlink escape despite lexical outputDir validation. The test initialized a disposable project and fixture repository, added hello-skill, replaced project/.agents/skills with a directory symlink to a sibling temporary external-skills directory, and placed external-skills/hello-skill/unmanaged.txt as a canary. Then skm install --project exited 0, deleted the canary and materialized SKILL.md under the external sibling. Literal probe stdout:
  {"init_exit":0,"add_exit":0,"install_exit":0,"install_stderr":"","external_canary_before":true,"external_canary_after":false,"skill_materialized_outside_project":true}
  All fixture paths were under a newly created temporary root, which was removed in finally; no user files were touched. Static mechanism: resolveProjectOutputDir uses lexical path.resolve/path.relative containment, while materializeSkill calls recursive removeIfExists on outputDir/name without realpath/symlink containment.
- No exploitability outside this local install scenario was tested. Treat as an unsafe overwrite/path-boundary behavior requiring a user to run install on a project with a symlinked output path, not as a remote vulnerability.
