## Claimed feature versus actual data model

README claims automatic conversation capture and cross-platform context transfer across ChatGPT, Claude, Perplexity, Gemini, and Copilot. The MV3 manifest injects a DOM content script on those browser sites (including `chatgpt.com`, `claude.ai`, etc.); this is **not** support for Claude Desktop Chat/Cowork/Code, local/self-hosted Claude Code, API-key gateway routing, or their session stores. A browser page match does not imply a native client adapter.

The content script scrapes rendered `textContent`, infers roles by alternating selector result indices, and saves only the last adjacent query/response pair per capture. Auto/manual capture creates flat records with a generated local id, page URL, ephemeral generated `sessionId`, provider, query, response and timestamp. The service worker stores these in a Map keyed by generated context id and Chrome `storage.local`; it does not group by stable source conversation id or serialize the full message/event history. The transfer UI requests the single latest context or a single selected pair. There is no ChatGPT export/Projects/Sections reader; no project/section membership; no branches, thread forks, parent/child/subtask graph; no tool calls/results, token/cost accounting, raw history archive, attachment/image/file asset capture or hash manifest; and no target-native conversation/session writer. It injects a text handoff into a browser input, not a resumable native session.

No Skills/MCP/plugin import, API-key gateway endpoint configuration, scheduled tasks, extension-to-extension session hierarchy, or Desktop mode adapter was found. The only API-key path is intended for optional summarization directly against hardcoded OpenAI/Anthropic API URLs; it is not an Anthropic-compatible third-party gateway configuration.

## Reproduced functional/privacy defects (synthetic-only)

1. **Popup initialization throws.** `popup.js:updateStatus()` looks up `id="status"`, but `popup.html` contains `status-indicator` and `status-text`, not `status`. A VM harness populated DOM elements from actual popup HTML IDs and reproduced `Cannot set properties of null (setting 'textContent')` during initialization. The API-key inputs also mismatch: HTML uses `openai-key` / `anthropic-key`; JS looks up `openai-api-key` / `anthropic-api-key`. `contexts.html`, `welcome.html`, and a manifest options page are absent although source code opens/references them.
2. **Clear-all does not clear the active service-worker Map.** Popup clears only `chrome.storage.local` key `contexts`; it does not message the background `ContextManager` to clear its in-memory Map. A synthetic VM saved a fake marker, ran the same storage removal, then requested recent contexts; storage was empty but the service worker still returned the marker (one record). This is confirmed for the worker's current lifetime; no real user data involved.
3. **Settings toggles do not map to the fields the UI reads.** `id.replace('-', '')` turns `use-llm-summary` into `usellm-summary` (and auto-capture into `autocapture`), while `updateUI()` reads `useLLMSummary` / `autoCapture`; the content script never consults the setting. A synthetic popup VM toggled summary off, but persisted `useLLMSummary` stayed `true` and an unrelated `usellm-summary=false` property appeared.
4. **Summary code ignores the toggle and uses only one latest pair.** `GET_CONTEXT_SUMMARY` calls `summarizeContexts()` which always attempts the OpenAI API first (and Anthropic second) when a key is present. In a no-network VM with a synthetic key and `settings.useLLMSummary=false`, the mock fetch recorded an attempted OpenAI request containing only a synthetic marker; background never read `settings`. This proves the code path only; no request left the machine. The current manifest lacks the API host permissions, so Chrome would deny those cross-origin requests absent a manifest change.
5. **Local secrets/context are not protected by application-level encryption or retention.** Source stores raw query/response, URL, generated session id, and API keys in `chrome.storage.local`, with no size cap/retention limit and silent storage errors. Chrome docs say local storage is not encrypted, is exposed to content scripts by default, and has a quota. A failed write can be silently treated as successful by the background. The `innerHTML` context-list renderer interpolates scraped query/provider text without escaping; treat source text as untrusted and at minimum a UI/markup injection risk (script execution was not attempted).
6. **Auto-capture runs regardless of the visible setting.** MutationObserver schedules capture from DOM changes; neither the content script nor service worker reads `settings.autoCapture`. The popup's setting key is misspelled as described above.

## Fit decision

Disposition: **not suitable as a migration engine or production dependency**. Retain only as narrow UI/interaction prior art for a user-triggered, lossy web-context handoff. Although this is the most directly named cross-platform context bridge found in this candidate slice, it is not a full conversation exporter/importer, does not preserve project/session hierarchy or source semantics, does not target Claude Desktop modes, has broken popup flows and a synthetic clear-all privacy defect. To build Nexus, model immutable source sessions/events/assets separately, explicitly mark lossy prompt handoff as a projection, enforce retention/secret boundaries, and verify native resume per target.
