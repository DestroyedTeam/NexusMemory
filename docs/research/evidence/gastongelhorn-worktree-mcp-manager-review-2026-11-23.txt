## Functional boundary against Nexus Memory

This is a Rust worktree/branch manager with a TypeScript stdio MCP server and a Tauri/React native macOS GUI. README says its interfaces share one Rust worktree core; the MCP server offers worktree/Git/merge/agent/workflow/environment tools. It can create separate Git worktrees, record task notes in generated `CLAUDE.md`/`.cursorrules`, claim a worktree, heartbeat/release the claim, and hand a code task to Cursor/Claude Desktop/Claude CLI. Those are useful **task/worktree isolation and handoff** ideas.

It is not a cross-Harness memory/session migrator. It does not read/write ChatGPT or Codex Project records, Section Groups, conversations, message/event/parent/child/fork graphs, continuation/interruptions, attachments/images/links, token/usage records, Skills inventories, plugin/MCP server definitions, personal memory, or scheduled tasks. Its `Session` is an MCP process/lock identity, not an archived conversational session. `CLAUDE.md` or `.cursorrules` are newly generated task context, not restored original transcripts. The MCP setup helper can register its worktree server in compatible IDE clients, including Claude Desktop, but does not import Claude Desktop Chat/Cowork/Code sessions or configure the user's third-party inference gateway/API key. No Claude Desktop 3P Chat, Cowork, Code, or local Claude Code history adapter exists. The documented native GUI target is macOS; no Windows `.exe` acceptance evidence exists.

Disposition: `WORKTREE_AND_AGENT_HANDOFF_REFERENCE_ONLY; NO_PROJECT_SECTION_SESSION_OR_MEMORY_MIGRATION; NO_DESKTOP_3P_API_KEY_SESSION_ADAPTER; LICENSE_METADATA_CONFLICT; SECURITY_AND_TEST_FINDINGS`. Retain only the shared-core/CLI/MCP interface pattern, per-worktree task isolation, explicit task-context handoff, and intended claim model as design references. Do not treat this repository as the Nexus Memory engine or as an authoritative SessionGraph format.

## Implementation and safety audit

CodeGraph was initialized and verified before broad source exploration: 146 files indexed, 1,714 nodes, 4,289 edges. Its generated `.codegraph/.gitignore` was retained with only `*` after removing the `!.gitignore` self-preserving exception; the disposable checkout's source tree remained clean.

1. **Allowlist is not a path-boundary check.** `mcp-server/index.ts` gates calls only when `args.repoPath` is truthy. `utils.ts:isRepoAllowed()` resolves paths lexically and uses `resolved.startsWith(path.resolve(allowedRoot))`, without a path-separator boundary or `realpath`; a sibling such as `/tmp/nm-allowed/project-evil` is accepted for allowlist `/tmp/nm-allowed/project`. An empty `WORKTREE_ALLOWED_REPOS` is falsy and therefore disables the restriction; unset defaults to allow-all. A disposable Vitest POC printed `ALLOWLIST_SIBLING_PREFIX_ACCEPTED true` and passed. This is an input-boundary flaw in local code, not evidence of remote exploitability.
2. **Audit log stores full tool arguments verbatim.** `audit-log.ts` appends `JSON.stringify(entry)` to `~/.worktree-mcp/logs/audit.jsonl`; no redaction/retention/permission handling is implemented. A synthetic context sentinel was written to a temporary HOME and read back: `AUDIT_CONTEXT_PERSISTED true FILE /tmp/nm-worktree-review-home/.worktree-mcp/logs/audit.jsonl`. Only synthetic data was used.
3. **Session guard misses the actual remove tool's path field.** `worktree-guard.ts:guardWorktree()` extracts only `wtPath` or `worktreePath`; `worktree-tools.ts:remove_worktree` schema and handler pass `path`. Server middleware calls the guard before routing, but a POC calling `guardWorktree("remove_worktree", {repoPath, path})` returned `null` (`REMOVE_GUARD_RETURNED_NULL true`) before any claim check. `handoff_worktree` also performs worktree creation/context injection but is absent from the guard's modifying-tool set. Thus the advertised cross-agent lock is incomplete for these operation shapes.
4. **Claims have multiple stores and inconsistent semantics.** Rust core stores `.git/wt-agents.json`; MCP explicit claims store `~/.worktree-mcp/agent-claims.json`; session guard stores a separate `session-claims.json`. Timeouts differ (Rust docs 10 minutes, TS explicit claims 5 minutes, TS session claims 3 minutes). Rust `is_heartbeat_stale()` compares only hour/minute and ignores the calendar date, so an old timestamp can appear fresh again when its time-of-day is within 10 minutes. Its test hardcodes `2026-03-09T15:30:00Z`; on this runtime date (2026-11-23) that test fails. The Rust `with_claims_lock` comment promises exclusive locking, but code only opens/truncates a lock file and holds its handle; it never acquires an OS/advisory lock. The separate TS JSON claim writes are also plain read/write with no file lock or atomic replacement.
5. **Additional test-caught classification defects.** Rust `diff_intelligence::categorize_file()` checks `lower.contains("/src/")`; Git emits repo-relative `src/main.rs`, which returns `None` and fails its unit test. `task_router::calculate_relevance()` awards 25 points per matching word; the test case `auth-feature` vs `work on auth` produces 25 while asserting `>50`, so that test fails. The task relevance model uses simple substring matching, not semantic context or session lineage.
6. **Destructive actions are advisory, not gated.** MCP descriptions ask agents to request confirmation, and a few tool names emit a warning to stderr; server code does not enforce user approval. `postCreateCommand`, user-defined workflows and hooks can launch commands. The runner uses `spawn(..., shell:false)` for the post-create command, which avoids shell parsing but still executes a caller-selected binary. Handoff is sequential and does not roll back a created worktree if later context injection or IDE opening fails. No destructive live worktree operation was performed.
