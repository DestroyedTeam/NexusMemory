SAFETY REVIEW / REPRODUCIBLE DATA-LOSS DEFECT
`src/core/trash.js:116-147` restores each manifest entry, records existing destinations as conflicts, and refuses to overwrite them. However, after the loop it removes the entire batch directory whenever `missing.length === 0`, even if `conflicts.length > 0`. Thus a restore conflict can permanently delete the only remaining trash copy while preserving the replacement at the original path. This contradicts the documented recoverable/conflict-safe behavior.

Synthetic-only reproduction (no real Harness or user files): create `original-to-restore` in a fresh temporary source, move it to a fresh temporary trash batch, write `replacement` at the original path, then call `restore(batch.id)`. Command is captured in `outerarc-agent-sweep-conflict-probe.stdout`; exit 0, stderr empty. Literal stdout:
`{"conflicts":1,"restored":0,"missing":0,"replacementPreserved":"replacement","originalTrashPayloadSurvived":false,"batchSurvived":false}`
The `replacement` survives, but the source payload and batch are both gone. The upstream test named `restore reports conflicts without overwriting` asserts only that replacement is not overwritten; teardown deletes its temporary trash root, so it does not check that the preserved source copy remains. Do not treat this checkout as safe to reuse for destructive work until the defect is fixed and a regression test verifies payload retention. No source changes were made here.
