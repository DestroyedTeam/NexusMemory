## Product scope

`mcp-manager` is a small Node CLI for registering local MCP source directories and writing server entries into six agent configuration files: Codex, Claude Code, Kimi CLI, Cursor, Cline and Aider. It supports global `~/.mcp-registry` or project `.mcp`, symlink-by-default or `--copy`, environment interpolation, dry-run, JSON output, config-file backups, a lock file and a basic `find` command. It does not read/write chat transcripts or session hierarchies; there is no ChatGPT/Codex Project or Section Group model, branch/task graph, attachments, tool-event history, token/cost records, schedules, Skills/plugins migration, cloud session access or resume identifier. It cannot serve the user-confirmed Claude Desktop 3P Chat/Cowork/Code session target.

The README/spec describes `experimental_restore` as lock restoration, but the implementation only checks whether lockfile paths still exist. A synthetic lock/remove/restore sequence returned one missing source path and did not recreate the registry entry or agent config. The spec's “project” mode also does not remain project scoped for agent configs: `registryDir` changes to `<cwd>/.mcp`, but each writer uses `os.homedir()`; a temp project run without `--global` created a global-home config file.

## Confirmed synthetic-only destructive/path-boundary probes

All probes were confined to `/tmp/nm-mcpmanager-217-poc/`. For registry path tests, `MCP_MANAGER_REGISTRY` pointed to a temp root and `--agent=not-a-real-agent` ensured no agent config path was touched. For config tests, `HOME` pointed to a temp home. No real home config, user file, secret, MCP process, server or provider was accessed/launched.

1. **Registry add path traversal + sentinel destruction.** Source `mcp.json` had name `../outside-target`; a temp registry already had a file sentinel at `/tmp/nm-mcpmanager-217-poc/outside-target`. `add` exited 0, stderr empty, stdout reported `registryPath: /tmp/nm-mcpmanager-217-poc/outside-target`; the sentinel disappeared and that outside-registry path became a symlink to the source directory. `validateMcpDefinition` only checks that `name` is a string; `addToRegistry` uses `path.join(root, definition.name)` without containment validation.
2. **Existing registry collision is recursively destroyed with no consent or backup.** `add --copy` with a safe name matching a synthetic registry directory deleted its `KEEP.txt` sentinel, copied the new MCP into that path and exited 0; no backup was created. The default symlink writer likewise calls `removePath(dest)` before creating the link. No overwrite confirmation protects source registry contents.
3. **Registry remove path traversal.** `remove ../outside-delete --global --agent=not-a-real-agent --dry-run --json` exited 0 and left the temp sentinel, confirming the preview path. The same command without `--dry-run` exited 0 and recursively deleted the synthetic directory outside the configured registry. `removeFromRegistry` joins the untrusted CLI name to the registry and calls `fs.rm(...,{recursive:true,force:true})` without containment/ownership validation.
4. **Project/global scope mismatch.** With a temporary `HOME`, a temporary project cwd and no `--global`, `add --agent=claude-code` registered under `<project>/.mcp/` but also created `<temp HOME>/.claude/config.json`. Thus “project mode” still changes a user-global agent config; it can leak a supposedly project-only MCP or credential to other projects.
5. **Credential written as plaintext with permissive mode.** Synthetic source declared `env.DEMO_KEY="env:DEMO_KEY"`; `--env DEMO_KEY=SYNTHETIC_SECRET_217` resolved the value and wrote it verbatim to a temporary Claude config JSON. Under the observed default umask, the new file mode was `0644`; output itself did not print the secret, but the config file contained it and backups can copy secret-bearing configs. All files were in fake HOME only.
6. **Remote HTTP entries lose their URL.** A temp definition with `type:"http"`, `url:"https://example.invalid/mcp"`, and placeholder `command` was installed through the Claude writer. The emitted config kept `command:"placeholder"` and `type:"http"` but omitted `url`. Schema requires `command` and does not validate/preserve `url`; `toServerConfig` returns only type/command/args/env. The CLI therefore does not implement valid remote MCP configuration despite enumerating `http`/`sse` types.
7. **Lock “restore” is only a presence check.** After creating a temp registry entry + lock and removing the entry, `experimental_restore -g --json` exited 0 with `count:1` and `missing:[.../registry/restore-demo]`; the registry entry stayed absent. It performs no restore, reinstall, config repair, or backup replay.

## Compatibility audit against current official surfaces

- **Codex CLI:** `~/.codex/config.toml` and `[mcp_servers.<name>]` is the one adapter whose base path/managed TOML approach aligns with current official examples. It still writes only basic command/args/env; a full current Codex config includes additional URL/OAuth, environment-reference, approval, enable/disable and timeout features.
- **Claude Code:** writer uses `~/.claude/config.json`. Current official MCP scope is user/local in `~/.claude.json`, project in `.mcp.json`; the specified writer path is not where the client reads MCP entries. Source: https://code.claude.com/docs/en/mcp.
- **Cursor:** writer uses `~/.cursor/settings.json`. Current official locations are `~/.cursor/mcp.json` and project `.cursor/mcp.json`; project and global precedence are not modeled. Source: https://prod.cursor.com/help/customization/mcp.
- **Kimi CLI:** writer uses `~/.kimi/config.json`. Current Kimi CLI documentation says MCP defaults to `~/.kimi/mcp.json`; newer Kimi Code generations also have their own `.kimi-code/mcp.json` surface. Source: https://github.com/MoonshotAI/kimi-cli/blob/main/docs/en/reference/kimi-command.md and https://github.com/MoonshotAI/kimi-code/blob/main/docs/en/customization/mcp.md.
- **Cline:** writer uses `~/.cline/mcp.json` and an array named `mcp_servers`. Current Cline CLI docs/code put the active file at `~/.cline/data/settings/cline_mcp_settings.json` (overridable by `CLINE_MCP_SETTINGS_PATH`); its MCP format is `mcpServers` object. Cline's own issue #11671 explains its older `~/.cline/mcp.json` documentation was incorrect: https://github.com/cline/cline/issues/11671.
- **Aider:** writer uses `~/.aider/.aiderrc` and a speculative `mcp-server:` line. Current Aider config docs describe `.aider.conf.yml`; Aider upstream still has open feature requests for native MCP client support (#3314 and #4506). This adapter is not validated, and the candidate itself warns its syntax may not match an Aider version: https://aider.chat/docs/config and https://github.com/Aider-AI/aider/issues/4506.

## Local gates and disposition

There are no test files beyond `test/fixtures`, and no `test` script. `npm run check` only runs `node --check` over source and exited 0. `npm run smoke` only prints `--help` and exited 0. These are syntax/CLI-surface checks, not config-writer integration tests. Package has no runtime dependencies; no GitHub CI/build/release evidence was present.

**Reject current writers for safe reuse.** Retain only the abstract idea of a versioned MCP registry after redesign: validate canonical names; enforce realpath containment; never recursively delete an unowned target; stage/copy with ownership receipts and rollback; model scope and agent profile/version explicitly; use official per-client schemas; keep secrets as env references or write secure permissioned files; include runtime discovery probes and real tests. This is an adjacent MCP ResourcePlane, not Nexus Memory session-history migration.
