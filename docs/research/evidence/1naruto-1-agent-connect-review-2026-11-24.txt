## What the implementation actually does
It is a **narrow coding-agent session continuity tool** for Cursor, Claude Code CLI, Codex CLI, and Pi. A single invocation migrates one native source session, scoped to the current working directory, through an ordered canonical event list into one new target-native session. The README's “all 12 directions” refers only to these four tools.

- Canonical type union: `user`, `assistant-text`, `thinking`, `tool`, `marker`. It retains text, timestamps, thinking text/signature, normalized tool name/arguments/output/error, and markers. It has no project/section/group graph, parent/fork/subtask/agent-session relationships, native message IDs, image/audio/video/attachment bytes, file/link references as typed objects, token/cost usage, permissions, memory, schedule or plugin/server configuration.
- Each reader intentionally chooses a resume-effective active transcript: Claude follows the latest non-sidechain `parentUuid` chain and applies compact relinks/snips; Pi follows last-leaf `parentId`; Codex applies `thread_rolled_back`; these become a **linear stream**. Abandoned branches are dropped and counted, not migrated as a tree. Cursor reads its bubble timeline. This can make a selected coding session resumable, but is not full-history/branch-graph preservation.
- Media is not lossless: Cursor replaces inaccessible selected images with a count-only placeholder; Claude/Pi readers extract text blocks and ignore image blocks; Codex writer writes `images: []`; Cursor writer initializes `selectedImages: []`. Canonical schema cannot carry media even if a parser found it.
- Usage/model fidelity is absent: Claude writer writes all token usage counters as 0 and uses model label `agent-connect/import`; Pi writes a zero usage/cost object and `model: imported`; Cursor writes `usageData: {}` and zero token counts; Codex writer uses a recent local Codex config template or an `openai` fallback. Codex thinking is degraded into ordinary commentary text. No source model/account/API key is transferred.
- MCP tool invocations are representable as transcript tool events, but MCP server configs/auth, Skills, plugins, schedules, and cross-harness memory are not migrated. The installed Claude slash commands only prompt Claude Code to run the CLI tool; they are not a Skill/resource importer.
- `claude` target writes only the CLI transcript file under `~/.claude/projects/<encoded-cwd>/<id>.jsonl`, using static `CLAUDE_VERSION='2.1.201'`; it does not create a Claude Desktop 3P `claude-code-sessions` metadata record, Chat/Cowork state, 3P project/group, plugin config or gateway profile. First-party docs say Desktop 3P Code embeds the Claude Code engine and has its own GUI session manager; its app-specific Code metadata lives under `Claude-3p/claude-code-sessions`, while transcript JSONL is in shared `~/.claude/projects/`. Whether a CLI-written transcript is discoverable/resumable in the Desktop 3P Code UI remains a **version-specific native test gate**, not assumed. Terminal `claude --resume` is the documented resume hint.
- It never invokes an LLM/provider API or requests an API key. The target uses whatever local CLI/provider configuration is already in effect. Therefore the 3P gateway credential and desktop configuration are not installed or migrated by this tool.
- The migration creates a new target session and reports, does not edit the source, and has no batch/deduplication. Reports are under a centralized app-data path with POSIX 0700 directories / 0600 files. If report writing fails after the native target write, the code reports that the target session already exists; there is no atomic rollback across the target store and report.
- Cursor `writeReady()` checks whether Cursor is closed (fails closed if process status cannot be verified); the SQLite writer inserts new rows in `BEGIN IMMEDIATE`/`COMMIT` and rolls back on error. Tests use disposable SQLite data, not the installed Cursor database.

## Synthetic safety probe: Codex context bleed
`configTemplate()` scans all local Codex rollout files by mtime and copies the newest non-Agent-Connect session's `model_provider`, `base_instructions`, and first `turn_context` into a new target Codex session—even when it belongs to another project. In an isolated `/tmp` HOME, a synthetic Codex source carrying only fake strings `SYNTHETIC_BASE_INSTRUCTIONS_CANARY` and `SYNTHETIC_TURN_CONTEXT_CANARY` was used; `codex.writeSession('/tmp/.../project', ...)` exited 0 and the newly written target rollout contained both markers. The target `cwd`/`workspace_roots` were rewritten to the new project, but the unrelated synthetic `turn_context` marker and `base_instructions` persisted. This proves the cross-profile template behavior without touching a real Codex profile or secret. Treat as context-contamination/privacy risk for reuse: require target config from an explicit scoped profile or safe defaults, never silently copy the newest unrelated session's instructions/context.

## Official Claude Desktop 3P storage/import contract (checked 2026-11-24)
First-party sources give a concrete target model:
- On macOS the app-specific 3P data tree is `~/Library/Application Support/Claude-3p/` (Windows/Linux differ). `local-agent-mode-sessions/` contains Chat/Cowork history, per-session working directories, uploads, outputs, memory/project-memory, and `audit.jsonl`. `claude-code-sessions/` stores Code session metadata (working folder/settings/title/summary), while transcripts live in `~/.claude/projects/`. The desktop app encrypts some saved API credentials with OS secure storage, but conversations, local configuration and other records have different protection and are generally not at-rest encrypted. Preserve data source and security labels; do not overwrite live stores.
- Current Unified Claude merges Chat and Cowork into a single home interface, while Code remains separate. Where Cowork VM is available, a home-message can start a Cowork session; where it is unavailable, it can be Chat. Mode is therefore version/runtime/capability-dependent, not a stable two-tab assumption.
- The official 3P import wizard is a one-time copy from **claude.ai** exports and earlier local Claude Desktop Cowork/Code sessions. It can also import a selected folder specifically containing supported Claude sessions; docs do not specify a generic ChatGPT import format. It restores some projects/custom sidebar groups, memory/instructions, schedules, plugins/skills and Cowork/Chat attachments, with explicit caveats: connector sign-ins, Code attachment files, permission decisions and some app preferences are not copied; project links are omitted; personal claude.ai exports omit project knowledge and conversation attachment file contents. The wizard's source-specific copy is not a generic cross-Harness writer.
- Code on 3P uses Claude Code's engine and inherits the same provider/gateway; Chat and Cowork use the Desktop 3P app's own local-agent session store. All three are in scope but require distinct target adapters and native discovery/resume tests.

## Disposition
High-value **coding CLI session adapter and fixture-driven native writer reference** for Cursor/Claude Code CLI/Codex CLI/Pi. Not a source adapter for ChatGPT/Codex App or ChatGPT Projects/Section Groups; not a full Session tree/asset/memory/scheduler migrator; not a Claude Desktop 3P Chat/Cowork target writer; and not a gateway/API-key configurator. It may inform a separate *local Claude Code transcript* prototype after its global Codex-context inheritance and field-loss behavior are handled. Do not claim cross-Harness migration success until the source/target native resume gates pass.
