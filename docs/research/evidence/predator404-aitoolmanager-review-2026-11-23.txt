## Synthetic data-loss probes (all in disposable `/tmp`, removed afterward)
1. **Enabling a mirror overwrites an unowned real directory.** Actual CLI `skill enable demo --harness claude-code --scope global` exited 0 without a collision warning/prompt. Preseeded `.claude/skills/demo/user-owned.txt` was deleted; directory became a symlink to the canonical `.agents/skills/demo`. Literal state output:
`{"mirror_is_symlink":true,"unowned_mirror_sentinel_exists":false,"import_collision_sentinel_exists":false,"imported_body":"new imported source"}\n`
   Source path: `enableSkillMirror` → `mirrorOne` → `createOrReplaceSymlink`; the last helper removes any existing path (including a non-symlink directory) recursively. `unmirrorOne` correctly refuses a real directory, but the enable path does not. Existing tests cover unmirror refusal, not enable collision.
2. **Import overwrites an existing canonical Skill without confirmation.** Actual CLI `skill import <source> --scope global` exited 0 and imported one same-named Skill; a synthetic pre-existing `user-owned.txt` in the canonical destination disappeared, replaced by the imported `SKILL.md`. The CLI import callsite has no confirmation/`--force`; `copySkillAndSeed` uses `copyRecursive`, which removes destination first.
3. **Promotion compares only SKILL.md, then replaces the whole directory.** A temporary project/global Skill pair had byte-identical `SKILL.md`, a project-only asset and a global-only user asset. `planSkillPromotion` returned `conflict:false`; `promoteSkill` removed the global-only asset, copied the project-only asset and replaced project canonical content with a symlink. Literal output:
`{"mirrorResult":{"targetIsSymlink":true,"unownedSentinelDeleted":true,"pointsToCanonical":true},"promotionResult":{"conflictReported":false,"globalOnlyAssetDeleted":true,"projectOnlyAssetCopied":true,"projectCanonicalNowSymlink":true}}\n`
   The CLI/TUI ask for confirmation but show source/destination paths, not a full tree diff; the conflict check only compares the primary `SKILL.md` (or the single command file). This is a data-loss risk for assets/references even after the user accepts the promote operation.
4. **MCP config writes can broaden file permissions.** A separate temp-only `addServer` probe started with a `.claude.json` mode 0600 and existing server; after atomic JSON rewrite with a synthetic bearer header, the mode was 0644, the synthetic value was plaintext, and the existing server remained. Literal stdout:

   `writeFileAtomic` creates a default-permission temp and renames over the existing file without preserving mode/chmod. This is a local config-secret permission issue; the token was synthetic, no user config/key was touched.
5. **Possible Windows path-separator gap (simulated, not a Windows runtime test).** `assertSafeItemName` rejects `/` segments and absolute paths, but does not split `\\` segments. On this POSIX run it accepted `..\\..\\..\\..\\outside`; `path.win32.join('C:\\Users\\test\\.agents\\skills', name)` resolves to `C:\\outside`. Because Windows Node uses `path.win32`, add explicit backslash/Windows path validation before claiming safe Windows support. This is a path-semantics simulation, not an executed Windows build.
