ACTUAL MODEL / ADAPTER BOUNDARY
- Local stdio MCP server plus CLI over a single SQLite/FTS5 database (default ~/.megabrain/megabrain.db). Database tables store four manually authored knowledge record kinds: rules, mandatory specs, “experiences” (what failed / fix), and golden snippets. Project scope is a string label; no Project object hierarchy, Section Group, ConversationSession, messages, turns, parent/fork/subtask edges, attachments, tool-call records, token/cost ledger, memory importer/exporter, schedule, or session archive exists in source/tests.
- README lists Claude Desktop, VS Code Cline/Roo/Continue, Antigravity IDE and llama.cpp. The integration is manually configured MCP; server entry point uses stdio transport. This is one local database shared by clients that can invoke the tool, not automatic no-AI migration or a cloud conversation importer. No ChatGPT, Codex, Claude Code Cloud, or API-key gateway session adapter was found. README's Claude Desktop config example does not distinguish Chat, Cowork, or Code. It proves neither mode-specific session support nor restoration of the user's “Destruction Era” history.
- `brain_consult`/`brain_load_project` return a formatted prompt; “MUST call” language is system/tool instructions, not runtime-enforced preflight. `brain_require_spec` stores a path/trigger/instruction string; it does not read or prove the file exists. Optional `verified_snippet` is stored as a Golden Pattern without an independent validation step.
- Good adjacent ideas: typed memory record classes, project/topic retrieval, FTS5, a local stdio MCP interface, explicit list/delete/stats tools, and provider-neutral client invocation. These are separate from source session migration fidelity.

- A synthetic in-memory DB inserted one rule, mandatory spec, experience and golden pattern under `org-one/secret-app`; a consult from `org-two/secret-app` retrieved all four. Literal stdout: `{"project_one_normalized":"secret-app","project_two_normalized":"secret-app","foreign_project_consult_project":"secret-app","foreign_project_sees_rule":true,"foreign_project_sees_spec":true,"foreign_project_sees_experience":true,"foreign_project_sees_pattern":true}`. This is a reproduced cross-project contamination/leak for common-basename projects, not merely a static concern.
- Broad unscoped interfaces also exist by design: listing with project `all` and the `megabrain://rules` resource expose all projects in the shared local database; deletion accepts a global integer record ID, not an authenticated project scope. This makes project labels organizational filters, not tenant security boundaries.
