IMPLEMENTATION OBSERVED
- Core model is `Project{ID, Name, DirectoryPath, CreatedAt}` and `Todo{ID, ProjectID, ProjectName, Description, Done, Priority, Notes, Tags, CreatedAt, UpdatedAt, CompletedAt, DueDate}`. One project groups todos; no nested Sections, Section Groups, session parents/children, conversation IDs or event stream. Git-aware current-directory detection resolves a project path; it does not identify a harness session.
- SQLite and Markdown backends share a storage interface. Backend migration copies Projects/Todos/tags. `MigrateData` creates destination rows in a loop without a transaction. `--force` only bypasses the non-empty target-dir guard; `openTargetStorage` opens the existing destination and does not clear it, so this flag is not an overwrite/replace transaction and errors can leave partial writes. Config is not auto-switched afterward.
- Export envelope is `version`, `exported_at`, `tool`, `projects[]`; each project has ID/name/path/todos; each todo has ID, description, done, priority, notes, tags, created/updated/completed/due timestamps. Export commands cover YAML, JSON, Markdown and SQLite; `toki import` reads only YAML. Project `CreatedAt` is omitted; importer creates new Projects with `time.Now()`, so that value is not preserved. Import is idempotent by IDs and skips existing records; it does not merge/update conflicts. Invalid optional update/completion/due timestamps are silently ignored, while invalid created_at is an error.
- Major reliability issue: `runImport` prints each project/todo error and continues, then returns nil. A partial import can therefore finish with a successful process exit and no machine-readable failure summary. `TestImportCommand` checks registration/flag/argument setup only; helper tests exist for ImportProject/ImportTodo, but no direct end-to-end runImport error/partial-import test was found.
- SQLite export copies only the main `.db` bytes with `io.Copy`; SQLite is opened in WAL mode. `TestExportSQLite` closes the database before exercising the file copy. Active WAL/multi-connection snapshot consistency is not demonstrated; treat it as a backup-fidelity risk pending a focused test, not as a proven data-loss event.
- MCP server runs over stdio; README shows Claude Desktop config and says any MCP-compatible client can connect. It provides 11 todo/project tools, 7 read-only resources and 6 task/workflow prompts. `toki install-skill` installs a Claude Code Skill. These APIs operate on Toki’s task DB; they do not import a ChatGPT/Claude session or write a client-managed Cloud Session.

NEXUS MEMORY FIT
- No ChatGPT Project/Section/Section Group source adapter; no Claude Desktop Chat/Cowork/Code session adapter; no local/self-hosted Claude Code transcript/session parser; no Cloud/API-Key session writer. No message turns, attachments/images/links, tool event timeline, fork/subtask/session graph, token billing, memory files or scheduled task source.
- The MCP design is only a general example of exposed todo/project CRUD and read-only resources. Toki Projects are task containers keyed by UUID/path, not chat Projects; MCP prompts are workflow templates, not imported per-session instructions.
- Reuse nothing as a “fidelity solution.” If ever integrating its task list, keep task-project links in a separate optional workflow plane and make activation/delete/data writes user-approved.
