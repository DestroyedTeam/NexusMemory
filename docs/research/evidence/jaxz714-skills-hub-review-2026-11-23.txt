The actual models are SkillInfo and SkillManifest metadata, with one platform string. ## Actual capabilities and limits

- CLI commands: search GitHub repositories, install, list, update, scaffold, publish, info and uninstall Skills. Targets are Claude Code (~/.claude/skills), Codex (~/.codex/skills), Cursor (~/.cursor/rules), .agents/skills and a generic Skills Hub directory. These are Skills folders only, not session stores.
- Registry search calls the GitHub API, sorts by stars and guesses one target from repository topics/description. It is heuristic classification, not compatibility testing. Install clones the full GitHub repo without a commit pin/content digest or target-specific transformation. An existing install is updated via git pull --ff-only.
- `main()` calls ensure_dirs before commands. A `list` invocation with HOME redirected to a temp directory returned “No skills installed yet” (exit 0), while creating all five target directory trees (Claude, Codex, Cursor, .agents and generic) and .skills-hub state there. No actual user home was used.
- The model has no canonical project/session, source lineage or dependency graph. `SkillManifest.dependencies` is metadata; install does not resolve dependencies. No tests directory, CI/test config or round-trip fidelity test exists in this 9-source-file checkout.

## Reproduced local update metadata bug

A disposable local bare Git remote and clone were created entirely inside the temporary HOME; no GitHub or other network was contacted. The synthetic installed.yaml record started with platform `codex`. Calling `update_skill()` succeeded against the local remote, but `_git_pull()` then called `_record_install(..., platform=None, ...)`, which stores `platform or "unknown"`. Observed state transition: platform codex → unknown after update, exit 0. This can make `list` lose the target platform label after routine updates.

## Additional source-level operational risks (not dynamically exercised)

- publish_skill runs `gh repo create ... --public` unconditionally; it exposes the current Skill repository publicly if the user invokes publish and does not provide a private-mode option. The publish workflow was not run.
- uninstall_skill trusts the path in installed.yaml and calls shutil.rmtree(path) without checking it is within one of the configured Skills roots. This is a local-registry integrity risk; no deletion POC was run.
- Installed records are keyed only by repo name, not owner/repo, so same-named repositories can overwrite registry entries. Platform inference prioritizes “claude” over “cursor” and “codex” if those words occur in text; it is not a compatibility proof.
- Dependency installation and full CLI smoke were done only in an isolated venv/temp HOME. No user Skill folder, credentials, GitHub API, `gh` authentication, published repo, provider, MCP server, or conversation/session data was accessed.
