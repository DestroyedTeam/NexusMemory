## Product fit and adapter coverage

`agentpx` is a plugin/resource installer: it reads a plugin manifest, Skills (`SKILL.md`), and MCP server definitions, then writes copies/config snippets into local Harness locations. The registry tracks plugin name/source/version/time, target Harness IDs, MCP server names, Skill names, environment-variable names and optional project mode. It does not retain content hashes, file ownership/backup data, paths for each write, or a session identity graph.

The 19 registered adapter IDs cover Antigravity, Claude Code, Cursor, Windsurf, Claude Desktop, Zed, generic Workspace, Hermes, OpenClaw, DeepSeek, Pi, Devin, Cline, Roo, Continue, Goose, OpenHands, Trae and Qwen. The type has no Codex ID. `workspace` is a generic `.mcp.json` plus `skills/` destination, not a native Codex adapter. `--project` routes to that generic Workspace adapter, rather than a project-specific branch of each Harness adapter.

The Claude Desktop adapter targets `claude_desktop_config.json` for MCP only; `getSkillsTargetDir()` returns `null`. It has no per-mode distinction for Desktop 3P Chat, Cowork, and Code, no Desktop local-session/archive handling, and no history importer. This does not meet the user's three separate Claude Desktop acceptance tracks.

The Claude Code adapter writes MCP servers to `~/.claude/mcp.json` and Skills to `~/.claude/skills`. Current first-party Claude Code documentation specifies user and local MCP scope in `~/.claude.json` and project scope in `.mcp.json`; therefore the candidate's `~/.claude/mcp.json` is inconsistent with the documented current canonical store. This is a source compatibility finding, not a claim that every legacy build ignores it.

There is no ChatGPT/Codex Project, Section, Session, message, event, branch, task/subtask, attachment, token/cost, schedule, or memory transfer schema. The project is relevant only as an adjacent ResourcePlane/package-manager reference and is not a Nexus Memory session migrator.

## Disposable synthetic probes (no user data, credentials, target Harness, or commands run)

1. **Manifest-path traversal is reproduced.** A temporary plugin manifest set `mcpConfig: "../outside.json"`; actual `discoverPlugin` followed the sibling path and returned its synthetic MCP server and value `NEXUS_SYNTHETIC_SECRET_SENTINEL`. Output fields were `mcp_server_keys=["synthetic"]`, `external_env_value=NEXUS_SYNTHETIC_SECRET_SENTINEL`, `source_manifest_mcpConfig=../outside.json`. Only the temp sibling file was read.
2. **Update skips executable-command trust confirmation.** Actual `updatePlugin` ran against a temporary project and local plugin source with `process.stdout.isTTY=true` and no explicit `yes`. The update passes `yes: options.yes ?? true` to `installPlugin`, so it replaced the synthetic MCP command from `trusted-old` to `sh -c echo UNTRUSTED_UPDATE_SENTINEL`, returned `true`, and did not show the trust confirmation. The shell command was only written to temporary JSON; it was never executed.
3. **Non-TTY add bypasses trust, even without `--yes`.** Actual `installPlugin` dry-run with a synthetic MCP server and `stdout.isTTY` unset completed without trust confirmation. A required environment variable was absent; non-interactive flow skipped prompting. Dry-run prevented disk writes and the configured command was not executed.
4. **Uninstall removes unrelated local content inside its Skill directory.** A synthetic Skill was installed into a disposable project's `skills/demo-skill`; a `LOCAL_NOTES.md` sentinel was then added manually. Actual `removePlugin` returned true and recursively removed the complete `demo-skill` directory (`local_notes_before=true`, `local_notes_after=false`).

These are local synthetic behavior probes, not upstream-reported CVEs or tests on any user environment. Never run a third-party MCP command merely to validate configuration.

## Relevance to Nexus Memory

Retain as design inspiration only: native per-Harness resource adapters, a target capability registry, preview/dry-run, clear source→target write plans, and support for installed Skills and MCP definitions. Reject as a direct dependency or session-transfer engine until it uses containment-safe manifest reads, ownership/content hashes, confirmation that cannot silently disappear in non-TTY/update paths, transactional writes with rollback, and conservative removal semantics.

For the confirmed target, keep separate adapters and tests for `desktop-3p/chat`, `desktop-3p/cowork`, `desktop-3p/code`, and `claude-code-local`. Never infer Desktop 3P session support from the existence of a Claude Desktop MCP config writer. No API key was accessed or serialized.
