## What it is — a Skill content catalog, not a migrator

The repo contains five Spanish-language Agent Skills: `planning`, `narrative-summary`, `visual-preview`, `code-audit`, and `test-audit`. `skills-catalog.json` groups them and declares dependency edges (`planning` → `narrative-summary` + `visual-preview`; `code-audit` → `test-audit`) and editable per-repository `project.md` templates. The package is not a transcript/project/session importer or export tool: no source conversation IDs, project or Section Group identifiers, parent/fork/task tree, turn/event log, attachment manifests, token accounting, or schedule adapter exists. It has no MCP server or harness-plugin package in this catalog. The optional `code-audit` calls `@ramon-sg/github-rest` as a separate runner dependency, not as a bundled MCP.

The durable cross-repo contribution is **reusable instruction content plus a configurable per-repository overlay**, not conversation memory. `project.md` stores target-repository rules, commands, path conventions and known cases; manager behavior excludes these editable files from the skill content hash and preserves them on update. This is useful ResourcePlane material but cannot reproduce the user's `Destruction Era` conversation/session history or ChatGPT Project / Section Group hierarchy.

## Format and target-path compatibility (official-source cross-check)

The open Agent Skills spec defines a directory with `SKILL.md` metadata/instructions and optional `scripts/`, `references/` and `assets/`. Codex's official CLI docs use `.agents/skills/` for project scope and `~/.agents/skills/` for user scope; its Responses API Skills are a different versioned bundle/reference mechanism. Anthropic's current Claude Code docs use `.claude/skills/` for project and local personal skills, while Cowork/Claude cloud sessions load skills enabled on the claude.ai account; local `~/.claude/skills/` does not load in those hosted sessions. Therefore the **content format can be a portable base, but installation path, discovery, invocation, permission semantics and hosted synchronization are harness-/mode-specific** (synthesis from the official contracts, not a claim that every harness implements the standard).

This candidate's README and its integration test default to `@ramon-sg/skills-manager` copying under `.agents/skills/`. They do not configure or test a `.claude/skills/` target. The separate lock-installed manager 1.1.0 supports a custom `paths.skillsDir`, but this catalog uses the default and this review did not conduct a full security audit of that manager. The README's claim that `.agents/skills/` makes the Skills available in Claude cloud sessions is **not established by Anthropic's current documented paths** and should be treated as unverified / potentially inaccurate for Claude Code Cowork/cloud; do not silently map that statement to Claude Desktop 3P. The official Anthropic docs consulted describe standard Claude Code/Cowork cloud, not every Claude Desktop on 3P release; direct 3P mode support still requires a versioned disposable-profile test.

Three Skills also use Claude-oriented frontmatter/body semantics (`argument-hint`, `context: fork`, `/slash` invocation, `ARGUMENTS`, `Claude Code SessionStart` and `project.md`). Claude Code documents `argument-hint` and `context: fork`; the base Agent Skills spec does not define these fields. Consumers that ignore unknown metadata may keep the text but lose behavior; strict consumers may need transformed frontmatter. Preserve the original bundle and emit per-target supported/unsupported semantics instead of claiming lossless portability.

Primary references: [Agent Skills spec](https://agentskills.io/specification); [OpenAI CLI Skill install paths](https://developers.openai.com/api/reference/cli); [OpenAI API Skills](https://developers.openai.com/api/docs/guides/tools-skills); [Claude Code Skills paths and frontmatter](https://code.claude.com/docs/en/skills); [Claude Desktop on third-party providers](https://support.claude.com/en/articles/18426225-move-from-claude-enterprise-to-claude-desktop-on-a-cloud-provider).

It binds `127.0.0.1` by default, requires a generated/token key for HTTP access, validates WebSocket origin, sets no-store/no-referrer and frame restrictions, and checks that served files are regular, single-link files whose real path stays under the content directory.
