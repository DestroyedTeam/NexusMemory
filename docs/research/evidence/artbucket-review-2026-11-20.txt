WHAT MAPS — AND WHAT DOES NOT
- Organizational shape is organization → project (a separate asset library) → collections/assets, brands, portals and project-scoped access grants. MCP `list_projects`, `create_project`, and `rename_project` select/maintain this DAM hierarchy; tools accept a `project` selector. A brand's pages can contain nested content sections (three levels at most), with version/history, comments and publication/release. These are useful as examples of explicit scopes and human-readable containment, but are not ChatGPT Project → Section Group → Session relationships. Collections are asset groupings, not chat folders.
- MCP is Streamable HTTP at `/api/v1/mcp`; the same application core backs REST and MCP. The documented agent connection uses OAuth 2.1 + PKCE/dynamic client registration and a consent screen for project/scopes; separately minted `ab_...` bearer keys are Artbucket API credentials, not Anthropic/Cloud model API keys. Scopes follow read/propose/write/admin, with proposals/approval gates. The frozen `/api/v1` contract and MCP tool schemas are valuable interface-governance references.
- It ships an Artbucket-specific Claude Code plugin/Skill about asset/brand workflow (`npx skills add pwnera/artbucket` is also documented). This teaches domain use; it is not a general Skill converter, MCP-server/settings importer, plugin bridge, or session adapter.
- It has a **brand/asset migration** flow, not AI history migration: docs explicitly state there is no connector for Frontify, Bynder, Brandfolder or Drive; the user uploads/downloads exports. A ZIP's folders can become collections; a brand book/PDF can become brand rules and draft pages. It presents a plan for human review before apply and permits undoing what the import added for 30 days. Its docs state external custom metadata, old links, licenses and people need separate handling. This is a useful migration-safety pattern (preview → review → apply → undo plus omissions report), but its source/target schemas are asset-management specific.

CONVERSATION / SESSION BOUNDARY
- The open-source app does include an assistant sidebar. Its client consumes a service URL surfaced as `ASSISTANT_URL` in `/api/v1/me`; the server implementation is a separate configured service, not in this checkout. The client stores only the current `chat` ID in browser `sessionStorage` (`assistant:chat`), loads `/chats/{id}`, lists recent chats per Artbucket project, and posts `/ask` requests carrying `{chat, question, asset, embed, where}`. The client models returned turns as question/answer/steps/actions and receives streamed events for chat ID, tools, working text, answer text, approvals/actions and errors.
- The repository's `src/app/api/v1` contains no chat/session/conversation route; `src/lib/db/schema.ts` has no chat/transcript tables (the only case-insensitive match is “ChatGPT” in an OAuth-client comment). No portable transcript import/export or Cloud session write route was found in the pinned source/API/MCP contract. Do not infer the externally deployed assistant service's internal storage, attachment retention, export, or Cloud capabilities from this UI.
- MCP itself is documented as stateless Streamable HTTP; a protocol session and an assistant `chat` resource are distinct things. This is an important design caution for Nexus: session identity, transcript graph and project hierarchy need source-specific owners/adapters, rather than equating a client UI's `sessionStorage` pointer with an exportable durable conversation.
