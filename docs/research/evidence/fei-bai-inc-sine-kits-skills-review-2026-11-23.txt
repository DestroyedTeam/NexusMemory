## Useful transferable protocol ideas

The two Skills recommend: one host-neutral authoring/usage Skill instead of per-Kit prompt copies; discover available operations dynamically; inspect bundled JSON Schema before constructing inputs; distinguish publisher login from owner-granted installation authority; separate declared capability from permission; require explicit user intent for persistent/provider effects; submit one stable idempotency key; poll the same durable run; and distinguish operation success from a record write or queued response. These are thoughtful **tool-execution protocol** practices for Nexus Memory's future MCP/provider adapters.

However, the repository does not enumerate or migrate any existing Harness Project, Section Group, chat Session, child/fork graph, transcript, attachment, Skills/MCP/plugin configuration, memory store, or scheduled task. It contains no Claude Desktop third-party-gateway **Chat**, **Cowork**, **Code**, or local Claude Code transcript adapter. The standard Skills are themselves AI instructions that invoke a network CLI and require an owner-operated browser consent flow; they do not meet a “no AI / no manual research” auto-migration target. The Skill role is not a universal Harness adapter just because it is host-neutral.
