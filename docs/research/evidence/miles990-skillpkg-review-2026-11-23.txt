## Product fit and actual implementation

The useful abstraction is a deterministic Skill ResourcePlane: skill manifests, source/dependency resolution, a local/global store, project-level skillpkg.json, simple state/dependency tree, and resource sync to Claude Code, Cursor, Codex and Copilot directories. The current Syncer target table maps .claude/skills, .cursor/skills, .codex/skills, and .github/skills. Official Codex docs still describe .codex/skills as a native skill directory. A project manifest may also define MCP server config, textual reminders and hooks. A configured MCP record is configuration data; it is not a converted historical session or a portable credential reference. The core syncMcpConfig method can write .mcp.json, but CodeGraph shows syncAll's only caller is syncer.test; CLI auto-sync and MCP sync_skills call syncToTarget, so current CLI/MCP install/sync flow does not invoke this MCP writer.

The data model is a single Skill with name/version/description/instructions/author/license/repository/keywords/triggers/capabilities/platform metadata and dependencies. skillpkg.json has project name, skill source map, MCP config, reminders, hooks and sync targets. These are package/project setup resources, not ChatGPT or Codex Projects/Section Groups, conversation Sessions, message/fork/parent-child event graphs, links, attachments, outputs, token usage, durable memory, or scheduled task state. No Claude Desktop third-party-gateway Chat, Cowork or Code session store reader/writer or gateway API-key/session adapter exists. README’s Claude Desktop MCP example merely configures an MCP server for skill management; it does not import/export any Desktop mode’s history or project/session structure.

Two subsystems have different formats and are not symmetric:
1. Syncer can write directory-form SKILL.md for the four platforms. The older AdapterManager/Importer uses Claude Code, a legacy .codex/agents Markdown format, Copilot’s merged copilot-instructions.md and Cline; it does not use the newer .codex/skills directory import route.
2. Importer returns one Skill object and only parses SKILL.md; its Skill type has no files/assets field. Exporter likewise writes one SKILL.md into dir/zip/tar/pack formats, not the full source directory.
3. CLI help lists no sync or migrate command. The README’s skillpkg sync examples are not executable: the built CLI returns exit 1, error: unknown command 'sync'. The v1.x-to-v2.0 MIGRATION.md command is also commented out in cli.ts; the built CLI returns exit 1, error: unknown command 'migrate'. install may auto-sync after install and the MCP server exposes sync_skills, but neither command provides session migration. The README's use of “migration” refers only to skillpkg’s own config/state format and plugin marketplace replacement.

## Isolated synthetic filesystem probes

All probes used a newly created temporary root under /var/folders/.../T; they did not touch user-owned skill/project directories.

1. Unowned output deletion: Syncer.syncAll on a project with an empty incoming skill map, but an existing .claude/skills/unrelated-user-skill/KEEP.txt, returned success and reported the directory as deleted; the sentinel did not survive. cleanupOrphans removes every directory missing from the current map without a skillpkg ownership marker.
2. MCP config loss: a pre-existing .mcp.json contained user_server; syncMcpConfig with imported_server returned action updated and rewrote mcpServers so only imported_server remained. Existing servers are not merged/preserved. MCP env strings are serialized directly into .mcp.json.
3. Skill-name path traversal: parseSkillMd accepted the synthetic untrusted name ../../store-escape; StoreManager.addSkill then wrote SKILL.md outside the configured .skillpkg store, at a sibling temp-root path. No name containment validation runs at parse/store boundary.
4. Export path traversal: Exporter.export with synthetic name ../export-escape and output=<temp>/exports returned success and wrote SKILL.md at <temp>/export-escape, outside the output root. A normal safe name also exported successfully.
5. Same-count asset drift: source and target had identical SKILL.md plus one reference file each, but source reference content was source-v2 while target held target-v1. Syncer.syncToTarget returned success/action unchanged because the SKILL.md hash matched and the additional-file check compares only file counts; target retained target-v1.
6. Codex Skill import mismatch and asset loss: a synthetic .codex/skills/demo-skill/SKILL.md plus references/guide.md was auto-detected as platform claude-code; explicit import with platform codex failed “File is not a valid OpenAI Codex format”. Generic folder import returned one Skill object containing schema/name/version/description/instructions only; the existing references/guide.md was not carried into the result.

## Disposition

Reject as a core Nexus Memory migration engine and do not use its sync/install/remove implementation as-is. Keep it as a historical medium-value resource-plane reference for declarative Skill/MCP source mapping and per-target serialization, because it correctly treats Skill payload and project package setup as first-class resources. Before borrowing any design, replace path construction with validated opaque IDs + containment checks, model ownership before cleanup, merge/preview/preserve unrelated MCP servers, stage writes with rollback, compare asset hashes/manifests rather than counts, and design loss-aware import/export. It fails all target acceptance tracks for ChatGPT/Codex Projects and Sections, session nesting/branches/transcripts, attachments/usage/memory/schedules and Claude Desktop 3P Chat/Cowork/Code session migration.
