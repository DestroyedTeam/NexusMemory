## Product boundary and native migration design

- High technical relevance: this is a deterministic, native **Codex ↔ DeepSeek Harness (DSH)** bridge, not generic prompt replay. It has separate Codex and DSH readers/writers, an explicit field-mapping layer, `inspect`/`migrate`/`install`, optional dry-run, generated target identity, a loss/tally report, and pending/unknown-tool operation reporting. The migration path says it makes zero model requests and executes zero tools.
- Codex input is a local `rollout-*.jsonl`; DSH input is `session.v3/v4.jsonl.zstd`, whose concatenated zstd frames are parsed explicitly. Codex output needs target-native thread registration and schema compatibility; DSH output is written to the target session artifact store. A target `cwd` is required/remapped, but project files are not copied.
- It handles only those two Harness formats. It does not read ChatGPT account exports/Projects/Section Groups or map to Claude Desktop Chat/Cowork/Code, Claude Code local sessions, Claude API gateways, other harness histories, Skills, MCP servers, plugins, schedules, or independent memory stores. Its own web/local chat history is a separate product store, not an importer for those targets.
- The design is intentionally lossy and reports why: e.g. encrypted Codex reasoning, foreign system/developer prompts, duplicate UI events, token-count records and DSH-only events may be dropped; tool names/arguments are preserved but the target may not recognize them; DSH step boundaries, streaming fragments, permissions/sandbox settings, some usage fields, agent/title events and non-text content have no equivalent. Compaction is treated as a replacement surface; unresolved tool outcomes are carried or refused instead of replayed. Images/offload projections and unsupported forms may be explicitly rejected.
- Hierarchy boundary: DSH parent sessions and `origin=subagent` are rejected by migration eligibility; there is no recursive parent/child migration or Project/Section graph. The source CWD must meet native resume requirements. No workspace files, attachments, MCP config, plugins, skills, schedules, or memory are bundled.
- Compatibility is version-sensitive. DSH is limited to v3/v4; Codex writing targets `state_5.sqlite` columns and Codex rollout conventions. The reader preserves unknown Codex records; the DSH writer is strict. This demonstrates why per-version target validation and a native resume check matter; it is not a stable universal interchange format.
- Safety strengths: preview/dry-run and inspect; refuse damaged or partial source; explicit absolute target CWD/home; UUID identity; no overwrite; Codex registry schema preflight; finite parser/decompression/upload limits; web migration uploads are handled in memory; no model call/tool execution; source logs remain separately untouched. The Codex install writes the rollout before SQLite registration, and reports an orphan rollout if registration then fails, so this is not a multi-store atomic transaction.
- Security tradeoff in its separate app: `SECURITY.md` says API keys and conversations are not encrypted at rest; Unix file modes are 0700/0600 and Windows ACL restriction is the operator's responsibility. Local CLI keys are read from environment variables rather than persisted in its CLI session DB. None of these secrets should be moved as values; use credential references and destination-side setup.

- `go vet ./...`: exit 0, empty stdout/stderr. `go test -race ./internal/cli ./internal/server ./internal/task ./internal/session ./internal/provider`: exit 0; all five packages passed.
- Node v26.7.0 tests ran with isolated HOME and empty `CODEX_SESSIONS_ROOT`/`DSH_SESSION_ROOT` (no personal history read): `codex-adapter` 12 tests, 7 pass / 3 fail / 2 skipped; `dsh-adapter` 14, 10 pass / 0 fail / 4 skipped; `contract` 72, 13 pass / 56 fail / 3 skipped; `cli` 66, 36 pass / 0 fail / 30 skipped. ## Disposition

**HIGH_TECHNICAL_VALUE_NARROW_MIGRATION_REFERENCE; NOT A NEXUS DEPENDENCY OR UNIVERSAL SOLUTION.** It is the strongest reviewed implementation pattern so far for deterministic per-Harness adapters, explicit fidelity loss, safe refusal of ambiguous/partial sessions, offline preview, and native target acceptance. Because the repository has no license, zero external adoption signals, no release or Actions runs, Windows-centered local integrations, and only the Codex↔DSH pair, retain it as a research/architecture reference only. Build Nexus independently, with a versioned adapter matrix and end-to-end target-native acceptance, unless licensing and destination coverage are later resolved.
