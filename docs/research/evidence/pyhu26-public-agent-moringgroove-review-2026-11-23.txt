## Product and actual data model
README/PLAN/source establish a local folder-based Claude Code companion: one registered filesystem directory is the work unit; each folder can hold one or more app-defined agents; each agent has its own UUID `id` and Claude Code `sessionId`; multiple agents in a folder share its files, MCP and Skills. Browser chat and herdr terminal use the same native Claude Code session. The “knowledge graph” indexes `<folder>/docs/**/*.md`. This is not a ChatGPT Project/Section hierarchy, nor a Claude Desktop Project.

Runtime metadata is a tiny local JSON store: `data/config.json` (roots/favorites/settings), `data/agents.json` (folder -> agent records/session IDs), `data/usage.json` (latest rate-limit windows), and regenerated `data/prompts/<agent id>.md`. Transcript persistence is delegated to Claude Code's `~/.claude/projects` JSONL files; the app does not own or export them. There is no source-side Projects/Sections/session-event schema, converter, archive, import/export command, or adapter for ChatGPT, Codex, Claude Desktop Chat/Cowork/Code, or other harnesses. A configured local `claude` CLI is required; an alternate executable path is possible, but there is no dedicated/validated third-party gateway/provider adapter.

`/api/chat/history` is a UI resume helper, not a complete archive: `getSessionMessages` is called with `limit: 200`; user history keeps text blocks only and filters command/system-reminder messages; assistant history keeps text and tool-use summaries, not tool results or attachment payloads; it drops historical parent-tool-use topology and token/cost usage. It returns an empty list on Windows-native because the transcript store is inside WSL. There is no branch/parent/child/fork import or export. Deleting an app agent removes the JSON metadata and stops its live runner but explicitly leaves the native transcript file. The static Markdown knowledge graph and per-agent system prompt are useful context assets, not imported conversation memory. Schedule support was not found; OS logon startup in the README only starts the local web server.

Resource-plane overlap is narrow: per-folder MCP in `<folder>/.mcp.json` (optionally inherit global Claude Code MCP), and per-folder Skills in `<folder>/.claude/skills/<name>/SKILL.md`; the Claude SDK loads user/project/local settings for its own Code runtime. This is not Desktop Chat/Cowork/Code portability or cross-Harness plugin migration.

## Security/data-loss probes (synthetic disposable temp only)
- Actual ephemeral local HTTP API test through `serve.mjs`, with a registered temporary project and `docs/external -> <temp outside>/` symlink: `PUT /api/doc` for `external/synthetic-route.md` returned 200 and wrote outside `docs`; `GET /api/doc` returned that external content. The helper checks lexical `path.resolve` prefix but does not resolve/reject symlinks. Literal stdout: `{"docs":{"putStatus":200,"readOutsideDocs":true,"outsideFileCreated":true},"mcp":{"putStatus":200,"newMode":"644","syntheticSecretPlaintext":true},"skillDelete":{"status":200,"unownedSentinelDeleted":true}}`; exit 0. This is a temp-only API test, not access to a user project.
- In the same isolated server process (umask 022), `PUT /api/mcp` created a temp `.mcp.json` mode 0644 containing a fake `TOKEN=SYNTHETIC_NOT_REAL`. UI/API accept MCP `env` values as plaintext config; README/PLAN mention `.gitignore`, but new files are not restricted to 0600.
- `DELETE /api/skills` removed an unmarked same-name Skill directory containing a synthetic `user-owned.txt`; UI handler issues the DELETE without a confirmation dialog. This is destructive if a folder's Skill directory contains unowned attachments/assets.
- Local server security is not uniformly absent: it binds `127.0.0.1`, validates Host/Origin, and checks requested folder roots via realpath. However, the docs symlink issue bypasses the lexical doc-root check. Default agent mode grants full Claude Code permissions; Ask/readonly exist as opt-down controls.
