Observed implementation
- TypeScript/Node MCP server and CLI package; Node >=20; MIT.
- Twelve MCP tools: detect_project, recommend_skills, preview_skill, list_installed, doctor, install_skills, remove_skill, sync, update_skill, list_profiles, define_profile, activate_profile. The stdio handshake advertised all 12. Six are annotated read-only; writes are exposed as separate tools.
- Resource targets are Claude Code's .claude/skills and Codex's .agents/skills. The resolver follows GitHub refs to immutable commit SHAs; lock entries include source SHA and SHA-256 content integrity. The local content-addressed store, path validation, 200-file/10-MiB caps, per-project lock, integrity checks and ref tracking are meaningful reproducibility mechanisms.
- Scanner is heuristic pattern matching, not AST or data-flow analysis. It assigns rule weights and requires explicit acknowledgeRisk at score 40; low/medium findings can proceed without that gate, so absence of a hit is not a safety guarantee.
- Profiles are named lists of Skill IDs; activation installs that set and removes other lock-managed Skill entries. They are not chat Projects, Section Group membership, session parent/child trees or branch/fork graphs.
- No ChatGPT/Codex Project/Section/session parser or writer, no transcript/message/event importer, attachment/token/usage mapper, cross-session controller-child relation, memory conversion, scheduled-task importer, or session fidelity test was found. There is no explicit adapter for Desktop's 3P Chat or Cowork. Code mode overlap is unverified; do not infer it from a .claude/skills target.
- MCP approval is described as a client/human gate in project documentation, not enforced by an explicit server-side confirmation parameter. install_skills is annotated destructiveHint=false despite filesystem writes. activate_profile is destructive and removes managed skills outside the chosen profile.
- Install path safety concern: uniqueDirName checks collisions only against entries in skills.lock, not an existing unmanaged directory. materialize calls linkSkill; clearExisting removes any real directory at the destination recursively. The unit test explicitly demonstrates stale contents disappearing when a real copied directory occupies the path. No ownership marker or preflight refusal is present in this path. Treat as a possible first-install clobber of a same-named unowned Skill directory; no user directory was touched in this review.
- Positive safety work: traversal/Windows-name checks, explicit score gate for high-scoring content, content hashing including binary bytes, capped resolution, pinned installs, and rollback of partial profile activation. These are worth studying, not sufficient for session import.
