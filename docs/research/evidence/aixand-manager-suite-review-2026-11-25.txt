## Verdict

**High-quality adjacent architecture, zero ChatGPT-to-Claude migration coverage.** This repository is a five-product suite—Agent, Conversation, MCP, Prompt, and Skill Managers—not a Harness archive converter. Preserve selected design references, but do not count it as a successful import, use it as the Nexus migration backend, or describe its native continuation as cross-provider migration. Its beta release notes explicitly say stateful rollback remains blocked until a migration-aware adapter exists.

## What the code actually does

### Agent Manager: same-provider continuation, not cross-Harness import

- Claude Code and Copilot can continue a retained conversation in another environment of the **same provider**. Claude reuses the original native transcript path under the destination `CLAUDE_CONFIG_DIR`; Copilot links the original session directory. The destination supplies its own provider login/settings. The manager does not copy credentials, transcript bodies, or replace the session; it rejects cross-provider continuation.
- The published qualified adapters are Linux-only and require exact provider CLI versions (Claude Code 2.1.316; Copilot CLI 1.0.105). This constrains claims to those versions/platforms; it is not a general desktop import protocol.
- OpenCode has a more migration-like **same-provider copy**: native standalone export/import into a destination OpenCode environment, preserving a Manager-level logical conversation identity and tracking copied revisions/ancestry/branches. It creates fresh native session/message IDs. Native export omits unfinished assistant responses/running work; child-session trees, runtime state, and external artifacts are not cloned. If environments change independently, the Manager keeps branches and requires explicit branch selection. The docs mark full export/import qualification as pending because the host must permit native server listening.
- This gives useful examples of *reference identity vs native ID*, copy lineage, revision digests, branch heads, explicit destination account selection, and refusing silent fallback. It does not ingest ChatGPT's archive/session graph or translate between providers.

### Conversation Manager: new retained conversations, not native history import

- The public API creates/attaches/listens to conversations recorded by its own store and retained workers. `client.conversations()` does not discover all provider-native history.
- It models operation receipts, messages/events/turns, approvals, pending input, queues, cancellation, reconnects, and (where supported) provider transcript reconciliation. The provider-backed saved transcript path is implemented for Codex; other adapters can return no transcript.
- Images/files, history search, message editing, and generalized branching are out of scope in the documented contract. A conversation `reference` preserves manager/native identity, but the suite does not provide a ChatGPT Projects/Section Group hierarchy or a full parent/fork/subtask session graph.
- This is useful **new-session runtime/event-lifecycle** prior art, not a history importer.

### MCP, Prompt, and Skill Managers: owned resource stores

- The managers import local/GitHub MCP definitions, prompts, and Skills into manager-owned stores and have explicit reconciliation/versioning/export workflows.
- Importing content is separate from delivery: the integrating application chooses when and where accepted content is installed. Opening a store does not automatically adopt existing Harness data. No project-session dependency graph, secrets/account credential migration, installed-plugin mapping, schedule importer, or target-specific ChatGPT/Codex/Claude Desktop configuration importer was found.
- These are relevant ResourcePlane ideas (ownership, provenance, immutable snapshots, explicit delivery), not evidence that arbitrary Skills/MCPs/plugins transfer with a session.

## Reuse decision

Keep only these implementation concepts for future Nexus design comparison:

1. Separate stable logical-conversation references from provider-native session IDs.
2. Record explicit source/destination identity, immutable transfer requests, operation receipts, idempotency and recovery states.
3. Model copy revision ancestry and multiple heads as explicit branches rather than silently merging/overwriting.
4. Separate ResourcePlane acquisition/review from application-specific delivery; retain provenance and hashes.
5. Treat native continuation as a constrained adapter with exact platform/version checks and provider-owned credentials.

Do not copy code wholesale or claim coverage until tests validate source archive parsing, destination-specific writes, project/section membership, attachment/tool-event fidelity, resource dependency detection, error recovery, and per-mode post-import reopen behavior. Candidate is **adjacent prior art, not a migration-engine finalist**.
