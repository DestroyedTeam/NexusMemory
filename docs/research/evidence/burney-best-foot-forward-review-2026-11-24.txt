## What the implementation actually models

BFF is a local-first job-search and career-memory application used through Claude Code, Codex, Gemini, and Antigravity skill workflows. SQLite is the authoritative structured store; generated JSON caches support agent reads; a Logseq graph mirrors the job-application pipeline. The database stores a domain schema: contacts/education/employers, achievement bullets and skill groups with tags, job descriptions and fit scores, applications/stages/follow-ups, interview contacts/assessments, STAR stories, and artifact-path registry. “Projects” in the README mean professional work/project history, not Harness Project objects or Section Groups. The graph pages are company/application/prep/notes entities, not chat/session hierarchy.

`stories.raw_transcript` can hold an interview/story transcript (`source_type` is audio/transcript/typed/conversation), but this is a structured career-story source field, not a transcript of the agent's own dialogue. `file_registry` records file paths, types, labels, and metadata; it is not an archive format for arbitrary session attachments. `follow_up_date` and counts are job-application follow-ups, not scheduled Harness tasks.

A narrow UAT run ledger (`tests/uat/uat_history.py`) stores run time, commit SHA, harness/model labels, score, error flag, cost, duration, turn count, and scoring-quality metrics. Its source explicitly excludes raw reply text and fixture PII. It provides **no token counts, full request/response turns, message parents, attachment blobs, or session-resume state**. This is useful evaluation-provenance prior art, not session telemetry migration.

## Cross-agent behavior: useful but bounded

- Workflow content is shared through `.agents/skills/` for Codex/Gemini/Antigravity; Claude Code uses `.claude/commands/` and a manually deployed global cleanup skill. The cleanup workflow distinguishes user raw notes from Claude analysis, saves selected artifacts/memory, checks outstanding work, and explicitly says not to preserve ephemeral session details. This is a good **agent-mediated selective handoff/provenance convention**, but it is a summarization choice made by an agent—not a deterministic, reversible transcript/event export.
- The project MCP server exposes nine task-specific tools: `get_career_profile`, `get_bullets`, `get_skills`, `get_profile_bundle`, `get_application_summary`, `search_stories`, `get_salary_benchmarks`, `get_active_leads`, and `sync_leads`. The last one imports only job-lead records into the primary job database. There is no general transcript reader or conversation/session importer.
- `/secondary` does perform an explicit cross-machine profile handoff through MCP. `get_profile_bundle` returns version 1, export time, selected JSON caches (`_bullets*.json`, `_skills.json`, `_contact.json`, `_education.json`, `_employers.json`) and one Claude Code `user_profile.md` file. It does not export the SQLite database, STAR-story table, application pipeline, Logseq files/assets, tool history, or agent conversations. It is a domain-specific grounding snapshot to score job leads offline.
- Source says the HTTP MCP transport is request/response and does not maintain server-side MCP session IDs. In a synthetic local stdio smoke test, `initialize`, `tools/list`, and `get_profile_bundle` succeeded with no API key and only synthetic fixtures. The observed bundle contained exactly version/exported_at/caches/memory; `memory` contained only synthetic `user_profile.md`, with no conversation/session keys.
- The optional HTTP server refuses to start without a token registry, compares bearer tokens with `secrets.compare_digest`, and stores the registry as gitignored data with mode 0600 when minted. It nevertheless binds `0.0.0.0` over plain HTTP; its docs expect LAN/Tailscale ACLs, and the token is a second layer rather than TLS. `SECURITY.md` says the sensitive SQLite database is plain/un-encrypted at rest and disk encryption is the user's responsibility. Local-first means no BFF-hosted data store, not that data never reaches inference: README says task context is sent to the user's chosen model provider.
- No Claude Desktop Chat/Cowork/Code adapter, ChatGPT export parser, target session writer, API-key/gateway profile manager, plugin/connector migration, or portable session graph schema was found. The UAT script's custom runner can replace the outer harness, but its comments say the delegated scoring subagent remains a Claude `Agent()` call; this is not provider-neutral conversion.

## Nexus disposition

**Direct migration fit: none. Adjacent memory/workflow value: high for a narrow subset.** Keep as a strong low-star example of (1) explicit domain-specific canonical memory, (2) separate user-vs-agent authorship/provenance, (3) offline profile bundle transfer over MCP, (4) shared Skills plus harness-specific workflow shims, and (5) local-first storage with clear privacy boundaries. Do not reuse its career schema as the Nexus canonical session schema or interpret its Logseq “pipeline” as Harness Projects. No direct code dependency recommendation.

For Nexus Memory, borrow the product principles—not the domain model: preserve exact source events and branches first; make any memory summary a derived, attributable view; version bundle schemas and enumerate omitted records; add attachment/blob transfer and source tombstones; and test per-surface capability/degradation for Claude Desktop Chat/Cowork/Code and local Claude Code/gateways. A periodic cleanup skill can be an optional human/agent-assisted last-mile, never a substitute for deterministic migration.
