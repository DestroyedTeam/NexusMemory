## What the product actually models

`tkmd` is a local Markdown project/task manager and MCP server for developer/agent task governance. Each task is a Markdown card with YAML frontmatter; the optional `project` field is a string/tag and dependencies use `blocked_by` / `blocks`. Local/global scopes, Obsidian Base views and a task dependency DAG are not a ChatGPT Project/Section/Section Group hierarchy.

It does have a useful **task-to-agent-session reference**: cards contain an active/latest `session_id` and a `sessions` list such as `claude: <id>` and `codex: <id>`. A separate append-only `.events.jsonl` records task actions and the associated session ID. `TaskEvent` fields are timestamp, task id, action, actor, session_id, from/to status, eval result and title—not conversation turns or tool/media payloads. There is no parent/child/branch graph between the sessions themselves.

`tk u <task>` synthesizes a host CLI resume command (`claude -r <id>`, `codex resume <id>`, `gemini -r <id>`, `opencode -s <id>`, `pi --session <id>`, and other mappings) and launches the installed CLI. `--print` displays the command instead. This relies on that local harness's own session store, binary and authentication; `tkmd` stores only the opaque ID/command string and does not export/import or reconstruct session content. The runner uses `Command::new(...).args(...)`, not a shell, but a stored full command or unknown agent/program is still executable local input when a user launches resume; Nexus must never auto-run imported command strings.

An isolated end-to-end probe used a disposable task store and a stub `claude` executable: `tk add` stored a synthetic Claude session ID; `tk show` and `tk u --print` generated `claude -r synthetic-claude-session-123`; `tk u` passed `-r` and the ID to the stub. `tk u --agent codex --set synthetic-codex-session-456 --print` added a second agent ID to the card and generated `codex resume synthetic-codex-session-456`. The final card had a latest `session_id` plus two `sessions` references; the event log contained only the task `created` event. No real Claude/Codex process, account, session or API key was used. This proves pointer serialization and CLI dispatch only, not a real provider resume or migration.

The stdio MCP server exposes nine task tools: `task_list`, `task_get`, `task_add`, `task_claim`, `task_eval`, `task_submit_review`, `task_note`, `task_complete`, and `task_cpm`. Session IDs can be attached to task add/claim/review/note records, but there is no MCP `session_resume`, transcript import/export, host MCP-config installer, or session importer. README's `skills/tkmd/SKILL.md` is a single operational skill for using this task manager, not a general Skills migration feature.

## Nexus value and transfer boundary

- **High-value adjacent design:** task dependency DAG, explicit local/global scope, per-task session references, multi-agent handoff list, session resume command map, event audit, deterministic CPM/DSM, human sign-off, and pinned verification receipts.
- **Not a session migrator:** no ChatGPT/Codex Project/Section archive reader, session transcript/event-tree store, user/assistant/tool turns, subtask conversation linkage, image/file/link attachments, token/cost history, portable MCP/plugin registration, user/project memory, schedules, or Claude Desktop Chat/Cowork/Code, local Claude Code, or Anthropic-hosted Cloud session writer.
- Do not conflate a task dependency edge with primary/controlled Session hierarchy, or a task `project` label with an app Project. A `session_id` link is a useful lossless metadata sidecar edge only when the original harness can still resolve the ID; after migration to another harness it may be unusable.
- Security: task `eval` values run as shell commands through MCP/CLI; user-configured `on_done` hooks are another execution surface. `on_done` is off by default and board-supplied hook config is ignored, which is a useful governance pattern. Imported task checks/commands must be inert data until explicitly reviewed; never run them during migration.

## Disposition

Classification: **strong adjacent task-orchestration / session-reference / human-approval reference; not a cross-harness session migrator**. Borrow explicit `Task → SessionReference` data separately from canonical `Project/Section/Session/SessionEvent` relationships. Preserve opaque source IDs as non-runnable metadata, do not claim they remain resumable across harnesses, and require explicit review before executing checks or session commands.
